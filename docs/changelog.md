- **The real cause of the persistent admin "Something went wrong" was the running server itself, not application code**: the process actually handling requests (`node dist/server.js`) was a **compiled build from over a month before the `admin` module existed** — logging out, stopping, and restarting that same process just restarted the same stale JavaScript every time, since `node dist/server.js` runs whatever was last compiled into `dist/`, not the current `backend/src`. That old build had no `/api/v1/admin/*` routes at all, so every request 404'd with `ROUTE_NOT_FOUND` — a code the frontend's `errorMessages.ts` map doesn't recognize, so it fell back to the same generic message the previous (correct, but insufficient on its own) `403`-retry fix was aimed at. Confirmed by running the exact `findAll` query directly against the live database (it returned the real pending worker profile correctly — the query was never the problem) and by inspecting the actually-running process (`Get-CimInstance Win32_Process`), which showed `dist/server.js` timestamped 2026-07-23 against `admin/service.ts` timestamped 2026-09-04. Fixed by rebuilding (`npm run build`) and restarting the process fresh — verified `GET /api/v1/admin/workers` now returns `401 Unauthorized` (route exists, needs auth) instead of `404`. **Going forward, prefer `npm run dev` (`tsx watch`) over `node dist/server.js` during development** — it always runs straight from `backend/src`, so there's no separate build step to forget; if you do use the compiled path, `npm run build` must be re-run before every restart to pick up backend changes.
- **Found and fixed the actual cause of "nothing shows in admin" (reported as `Something went wrong` on the Pending tab): the access token's `role` is baked in at login time and never re-checked against the database per request.** `authenticate` decodes `role` straight from the JWT payload — it never re-queries `accounts`. An account promoted to `admin` *after* its current token was already issued (the realistic path: `backend/scripts/seedAdmin.ts` only ever runs before someone's first login; a manual DB promotion of an already-logged-in account is what actually happened here) keeps failing `authorize('admin')`'s `403` on every `/admin/*` call, even though `RequireAdmin`'s own fresh `GET /auth/me` check (added in the previous pass) correctly shows `role: 'admin'` and lets the dashboard render — `/auth/me` re-reads the account row fresh; the JWT itself doesn't. The generic fallback message (rather than the mapped "You don't have permission" one) was the tell: the failure was a network-level `fetch` rejection or an unparsable body in some cases, not always a clean JSON 403. Fix: confirmed `AuthService.refreshAccessToken` already re-reads the account from the database and signs the new pair from *that* (not the old payload) — so `admin-web`'s `apiClient.ts` now retries once via the same single-flight `tryRefreshAccessToken()` on `403`, not just `401`. A single silent refresh mints a token with the current role and the retried request succeeds — no disruptive forced re-login. If the retry still 403s, the account genuinely isn't `admin` and the error surfaces normally. Verified with a clean `tsc --noEmit` and `vite build`.
