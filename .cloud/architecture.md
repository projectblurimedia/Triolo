# Architecture

## Style

Modular Monolith. Three layers:

```
Presentation (mobile app / admin web)
        ↓
Business Logic (Express controllers → services)
        ↓
Data Access (repositories → PostgreSQL)
```

The UI never talks to the database directly; every request goes through backend APIs.

## Backend Module Boundaries

Each feature is an independent module under `backend/src/modules/<name>/`:

```
auth/
users/
workers/
businesses/
staff/
booking/
orders/
notifications/
admin/
ratings/
reviews/
search/
verification/
audit-logs/
```

Each module contains:

```
routes.ts
controller.ts
service.ts
repository.ts
validation.ts
dto.ts
interfaces.ts
tests/
```

Modules communicate only through each other's service interfaces — never by reaching into another module's repository or internal state directly. This is the boundary that makes future microservice extraction possible without a rewrite.

**`admin/` (implemented: list + verify Worker/Business profiles) is the first module that actually needs another module's data** — reviewing `worker_profiles`/`business_profiles.verification_status` is its whole point. It respects the boundary rule above by having no repository of its own at all: `AdminService` depends on `WorkersService`/`BusinessesService`, calling admin-facing methods added to *those* modules (`adminListProfiles`, `adminGetProfile`, `adminSetVerificationStatus`) rather than querying `worker_profiles`/`business_profiles` directly. Those methods' own repository implementations do `JOIN accounts` for review context (`accountFullName`/`accountMobileNumber`/`accountEmail`) — a same-module query against a FK-related table, not a cross-module reach; the boundary rule is about which *module* touches which *table*, and `workers`/`businesses` already own `worker_profiles`/`business_profiles` regardless of who's asking. `admin`'s own routes wire up their own `WorkersService`/`BusinessesService` instances (backed by the same shared `pool`) rather than reaching for a shared singleton — matches how every module's `routes.ts` already instantiates its own repository/service/controller independently; there's no DI container in this codebase. `admin` accounts are provisioned via `backend/scripts/seedAdmin.ts` (`npm run seed:admin -- <mobileNumber> <fullName> [email]`), never self-registered (see Account Model) — the admin then logs in through the **existing** `/auth/login/*` flow, zero new auth code.

## Frontend Structure (user-app/)

Feature-based, mirroring backend modules:

```
src/
  screens/        (auth, home, services, lists, bazaar, user, worker, business, orders, booking, notifications, profile, settings, admin)
  components/     (shared: buttons, cards, inputs, dialogs, loaders, icons, GradientHeader)
  navigation/     RootNavigator (language + theme hydration gate → auth vs. app), AuthNavigator (stack),
                  AppNavigator (bottom tabs)
  services/       (API clients per module)
  hooks/
  state/          Zustand stores, incl. themeStore (theme mode, persisted)
  theme/          colors (brand-constant + light/dark palettes), useThemeColors hook, typography/fonts — Poppins app-wide
  localization/   (en, te)
  utils/
  constants/
  assets/
```

Post-login navigation is a bottom tab bar (`@react-navigation/bottom-tabs`): Home, Services, Prepare List, Bazaar, Profile. ("Bazaar" — the shop-ordering tab was originally named "Shoppify"; renamed to avoid trademark confusion with Shopify and because it reads more naturally in both English and Telugu, "బజార్". "Services" — originally a "Search" tab; the free-text search input lives on Home instead now, and this tab is for browsing by service category. "Prepare List" — added mid-session as an explicit product decision, a 5th tab in the middle of the bar with a `list-check` leading/tab-bar icon (a checklist glyph, switched from an initial `plus` per follow-up feedback — better matches "preparing a list" than "adding" one); `screens/lists/PrepareListScreen.tsx` is a placeholder, same pattern Services/Bazaar started as, with no `ServicesHeader`/`BazaarHeader`-style wrapper since it needs no local UI state yet — it uses the default `screenOptions`-provided `GradientHeader` directly.) Every tab screen is topped by the shared `GradientHeader` component (brand gradient, currently `#0055D3` → `#1D76FA`, constant across themes) — new tabs/screens follow this same header pattern rather than each screen rolling its own. `GradientHeader` supports `showBack` (circular icon-only back button, used on Auth-stack screens instead of the platform-default header), `leadingIcon` (decorative icon beside the title — every tab has one, matching its tab-bar icon: compass for Home's brand header, concierge-bell/list-check/store/user for Services/Prepare List/Bazaar/Profile — its glyph and circular background (`leadingIconButton`, 46px) are both deliberately bigger than the shared `iconButton` (40px) used by the header's back button and right-side actions, since only the leading icon was asked to grow, not every icon in the header), `subtitle` (short tagline under the title — every tab has one, including Home, so no header is just a bare title), and `actions` (right-side buttons — circular icon-only by default, e.g. Home's/Services'/Bazaar's own menu icon; a `HeaderAction` can also carry a `label`, which renders it as a labeled pill instead, for any future header action that needs one — none currently do, since Services/Bazaar's own profile-edit pill was superseded by a body card, see below). Title uses a semi-bold font weight — deliberately between the original bold and an earlier too-light medium pass. Services, Prepare List, and Bazaar are placeholders until the Worker/Business search, list-preparation, and shopping-list modules exist; Home's search bar and filter chips are UI-only for the same reason. Their content should replace the placeholder in place, not add new tabs, unless a product decision changes the tab set (as it did for Prepare List).

**Home, Profile, Services, and Bazaar are exceptions to the shared header**: all four use their own wrapper (`HomeHeader`, `ProfileHeader`, `ServicesHeader`, `BazaarHeader`) instead of the generic per-tab `GradientHeader` config, because their header-triggered UI needs local state (modal/drawer visibility, or a fetched profile driving whether an action icon even shows) that a stateless header render function in `AppNavigator`'s `screenOptions`/`Tab.Screen options` can't hold. `ProfileHeader` wraps `GradientHeader` plus `ProfileMenuModal` (a bottom sheet — language/theme/logout, previously inline in the screen body); its trigger action uses the same `bars` icon every other tab's menu action uses (was `ellipsis-vertical` — the mismatched glyph, not the bottom-sheet-vs-drawer/dock behavior itself, was the "how is it like that" inconsistency per follow-up feedback; the menu's own presentation style still deliberately varies by content shape, see below). `HomeHeader` wraps `GradientHeader` plus `HomeMenuModal` (a right-side drawer — nearby-worker/shop discovery entry points plus theme/logout, modeled after a reference drawer-menu design: gradient header with an app icon, sectioned list of gradient-icon-square cards with title/subtitle/chevron, an app-settings section, and a footer). `ServicesHeader`/`BazaarHeader` wrap `GradientHeader` plus (respectively) `WorkerProfileModal`/`BusinessProfileModal` in edit mode — see the edit-mode note further below. Any future screen needing header-triggered local UI (a menu, a popover, a conditional action) should follow this same wrapper-component pattern rather than trying to lift state into the navigator config — and pick bottom-sheet vs. side-drawer based on content shape (a handful of settings toggles vs. a scrollable list of navigation entries). **Profile's body is gated on capability existence, not `accounts.role`** (which is always `'user'` for every self-registered account — see Account Model) — sections render per-capability, checking whether `useMyWorkerProfile()`/`useMyBusinessProfile()` resolved a profile, not any role field. For each capability that exists, Profile shows a `ProfileStatsRow` (`components/ProfileStatsRow.tsx` — a small row of icon+value+label tiles, modeled on a reference design the user shared) directly above the *same* `WorkerProfileCard`/`BusinessProfileCard` already used on Services/Bazaar (reused, not duplicated — each card's own `pen` button is the only edit entry point now; an earlier flat "manage profiles" link list was removed as redundant once the cards themselves render here). The stats themselves (Rating, "Services Completed"/"Orders Fulfilled") are placeholder values (`profile.servicesDoneValue`/`ordersDoneValue`, English+Telugu) until the ratings/reviews and booking/order modules exist — same placeholder honesty as the pre-existing rating value, just no longer a dead-end empty-image "Recent Work" grid alongside it.

**Profile's own top card is a `headerGradient` hero card, not a flat bordered row** — a translucent circular avatar (initials), name/mobile/email in white, and an "Active Account" status pill, the same gradient-hero-card identity `partner-app`'s `ProfileScreen`/`MyInfoScreen` already established (see that section below) — brought to `user-app` per feedback that the original flat card looked poor. The screen body is wrapped in a `ScrollView` (it wasn't originally — a plain `View` inside `ScreenContainer`, which is fine for short placeholder content but not once a hero card plus up to two capability sections are all present at once). An account with neither capability shows an explicit `profile.noCapabilitiesTitle`/`noCapabilitiesMessage` card (pointing at `partner-app`/`registration-web`) instead of an empty screen.

**Home's menu drawer** (`HomeMenuModal`) surfaces two discovery entry points — "Nearby Workers" and "Nearby Shops" — that each open `NearbySearchModal` (`components/NearbySearchModal.tsx`) in the corresponding `mode`, rather than navigating to the Services/Bazaar tabs. This replaced an earlier pair of entries, "Are You a Worker?" / "Do You Have a Shop?", which opened `WorkerProfileModal`/`BusinessProfileModal` in create mode to add a capability directly from `user-app` — removed per product decision, since Worker/Business **registration** now happens exclusively through `partner-app`/`registration-web` (see those sections below), and offering it a third time here was redundant. `user-app` still supports **editing** a capability that already exists on the account — `ServicesScreen`/`BazaarScreen`'s own profile cards and Profile's capability sections above still open `WorkerProfileModal`/`BusinessProfileModal` in edit mode via their `pen` buttons; only the creation entry point moved out of this app. `HomeMenuModal` still carries an "App Settings" section (Language, Theme, Logout) so all three are reachable from Home too, not just Profile's own menu.

**`NearbySearchModal`** is a full-screen modal sharing `WorkerProfileModal`/`BusinessProfileModal`'s own chrome pattern exactly (gradient header, left-side circular `chevron-left` back button) — but always the constant brand-blue `headerGradient`, for **both** `'worker'` and `'business'` mode. An initial pass gave `'business'` mode `SHOP_GRADIENT` (the orange Business-capability color, matching `BusinessProfileCard`/`BusinessProfileModal`'s own convention); per explicit follow-up instruction this was removed and must not be reintroduced here without being asked again — `NearbySearchModal` is a discovery/search surface, not a capability-identity surface, and stays blue regardless of mode. The search `TextInput` sits in its own card **below** the gradient header, not inside it — styled like `HomeScreen`'s own search bar (`colors.surface` background, `colors.border` outline), not translucent-on-gradient — per earlier feedback that the search bar shouldn't live inside the header. The result body is a coming-soon placeholder, not a search backend call — Worker/Business **discovery** (radius search over the `latitude`/`longitude` already captured on every profile, per the Search Architecture section below) is still Pending Module 4, not built yet; this was a deliberate scope decision (build the UI shell now, wire it to a real endpoint once that module lands) rather than fabricating result data or building the full discovery module as a side effect of a menu-item fix. The `query` state is already wired up and ready to drive that future call — swapping the body for a real result list shouldn't require touching the header/search-bar code at all.

**Skill/category chips are multi-select, not single-select** in both `WorkerProfileModal` and `BusinessProfileModal` — a worker can have several skills, a shop can span several categories. Each fixed chip's active state is `array.includes(key)` toggled on press (add/remove from the array), not a single selected-key comparison. `BusinessProfileModal` additionally has a Yes/No delivery-availability chip pair; selecting "Yes" reveals a `deliveryPricePerKm` `TextField` (backend-required in that case). All of these fields are JSON-stringified (arrays) or stringified booleans/numbers client-side before being appended to the `FormData`, since multipart fields are all strings — see `backend/src/common/utils/parseMultipartField.ts`'s `parseJsonIfString`/`parseBooleanIfString` on the receiving end.

**`"other"` is a dedicated "+ Add New" chip, not one of the toggleable category options** — `SKILL_CATEGORIES`/`SHOP_CATEGORIES` no longer include an `"other"` entry at all; instead, an always-visible `+ Add New` chip is appended after the fixed grid (and after any already-committed custom entries), rendered the same way regardless of state, so it's always available to add another. It's a filled tinted pill, not a dashed outline — `borderColor: accentColor` + `backgroundColor: ${accentColor}16` (a light alpha tint, matching `LocationPicker`'s detect-button tint convention) plus a small solid-fill circular badge (`addNewBadge`, 16px, accent-colored background with a white `plus` glyph) instead of a bare icon, reading as a deliberately-designed action chip rather than a placeholder/disabled-looking dashed box. Tapping it opens an inline `TextField` + circular gradient "Done" button (`otherInputValue`/`showOtherInput` state). Confirming (the Done button or the keyboard's own `returnKeyType="done"`) resolves the typed text in this order: (1) if it case-insensitively matches one of the fixed grid's translated labels (e.g. typing "Grocery"), that fixed chip is selected instead of creating a redundant custom tag; (2) else if it case-insensitively matches an already-committed custom entry, that existing entry moves to the front of the array (visible feedback that "you already added this" rather than a silent no-op or a duplicate); (3) else it's appended as a new entry. Either way the input clears and closes — tapping `+ Add New` again reopens it for another entry. Each committed custom entry renders as its own small removable gradient chip (tapping one removes it by index, since it isn't a fixed key with array-membership toggling). At submit time, if any custom entries exist, `"other"` is appended to the fixed-category array being sent and all entries are joined with `", "` into the single `otherSkillDescription`/`otherCategoryDescription` string the backend's `.refine()` validation expects (the backend has no concept of *multiple* other-entries — the join happens client-side).

**The fixed category grid re-sorts selected-first on every render** — `orderedSkills`/`orderedCategories` is a fresh `[...BASE_LIST].sort((a, b) => Number(selected.includes(b.key)) - Number(selected.includes(a.key)))` computed each render (JS's `Array.sort` is stable, so ties keep their original relative order), not a `useMemo` — the list is short (7-8 items) so re-sorting on every keystroke elsewhere in the form is cheap, and memoizing would need `selected` in the dep array anyway, i.e. no real saving.

**`WorkerProfileModal`/`BusinessProfileModal` double as edit forms**: an optional `profile` prop (the existing `WorkerProfile`/`BusinessProfile`, or `undefined`/`null`) switches the whole modal between create and edit mode (`isEditMode = !!profile`) — same form, same validation, same chip/tag UI, just prefilled via a `useEffect` keyed on `[visible, profile]` (skill/category arrays split into fixed-grid keys vs. `otherSkillDescription`/`otherCategoryDescription`.split(', ') for the custom tag chips, existing photo URLs turned into `PickedImage`-shaped entries so `ImagePickerField` can show and let the user remove them like any other picked image). Submit branches to `useUpdateWorkerProfile()`/`useUpdateBusinessProfile()` instead of the create mutations; photos are split back apart at submit time by `uri.startsWith('http')` — remote ones go to `existingPhotoUrls` (kept, not re-uploaded), local ones go through the same multipart file upload as create. Edit mode also shows a red "Delete Profile" text action at the bottom, gated behind a new generic `ConfirmModal` (`components/ConfirmModal.tsx` — parameterized icon/gradient/title/message/confirmLabel, factored out of what was previously `LogoutConfirmModal`-only so other destructive confirmations don't need their own one-off modal) calling `useDeleteWorkerProfile()`/`useDeleteBusinessProfile()`.

**Three entry points open the same edit-mode modal**: Home's menu still creates (`profile` omitted); `ServicesScreen`/`BazaarScreen`'s own `WorkerProfileCard`/`BusinessProfileCard` (rendered at the top of the screen body once `useMyWorkerProfile()`/`useMyBusinessProfile()` resolves a non-null profile — see below) carry the edit action; and Profile screen's own "Manage Your Profiles" section (tappable rows, shown only for whichever capabilities exist) opens the same modals directly from the screen body. All three just pass the already-fetched profile into the same `WorkerProfileModal`/`BusinessProfileModal` — there's no separate "edit screen." (`ServicesHeader`/`BazaarHeader` themselves no longer carry any profile-dependent UI — see the header-menu note further below for why that moved out of the header entirely.)

**Worker/Business profile summary cards, not a header pill, once the profile exists** — `WorkerProfileCard`/`BusinessProfileCard` (`components/`) render at the top of `ServicesScreen`/`BazaarScreen`'s body: fixed skill/category chips plus any custom "other" entries (split from `otherSkillDescription`/`otherCategoryDescription` the same way the edit-mode prefill does), a shared `VerificationBadge` (`components/VerificationBadge.tsx` — maps `verification_status` to a color/icon/label, reused by both cards so the mapping isn't duplicated), experience-years or delivery-availability, and location — plus a `pen` edit button opening the same `WorkerProfileModal`/`BusinessProfileModal` in edit mode. This replaced an earlier header-pill approach (a `HeaderAction` with a `label`, shown in `ServicesHeader`/`BazaarHeader` only once the profile query resolved) — the pill popping into the header chrome after the tab was already visible read as a UI glitch; a card appearing in the body as data loads in is a much more expected pattern. `BusinessProfileCard` imports `SHOP_GRADIENT` from `BusinessProfileModal` (exported from there) rather than redefining the orange gradient.

**Services/Bazaar's header menu icon opens a full right-side drawer, matching Home's own** (`ServicesMenuDrawer`/`BazaarMenuDrawer`) — `ServicesHeader`/`BazaarHeader`'s right-side action is still a plain `bars` icon (matching Home's own header exactly). This replaced an earlier compact floating icon dock (`SideDockMenu`, now deleted — a 72px rounded panel anchored below the header with stacked icon+label buttons and placeholder Filters/Sort/Favorites/History-or-Orders items) per explicit feedback that these two tabs' menus should look and behave like Home's drawer instead of their own distinct, more minimal pattern. `components/SideMenuDrawer.tsx` is the extracted shared shell (gradient header with a brand icon + title/subtitle + `xmark` close button, slide-in-from-right `Animated.timing` chrome, scrollable body) — the same interaction pattern `HomeMenuModal` established, pulled out once a second and third tab needed it too so it isn't tripled; it takes `children` for the body rather than a rigid item-list prop, and `components/DrawerMenuItem.tsx` is the shared gradient-icon-square-plus-title/subtitle-plus-chevron row (same shape as `HomeMenuModal`'s own items) that both new drawers compose their sections from. `HomeMenuModal` itself was deliberately **not** refactored onto this shell — its body mixes plain nav rows with settings rows (dynamic "current value" subtitles) and a distinct red logout button/footer, different enough from a flat list of `DrawerMenuItem`s that forcing it through the shared shell wouldn't simplify it, and it's shipped, working code not worth the regression risk to rewire for its own sake.

`ServicesMenuDrawer` has two sections: "Get Help" (**Quick Book** — search/book a worker directly; **Post a Problem** — describe a non-emergency issue so nearby workers can pick it up, the user-facing name for the broadcast-style discovery already described in the Search Architecture section below) and "Manage" (**My Bookings**, **Favorite Workers**). `BazaarMenuDrawer` mirrors it with shop-domain equivalents: "Shop" (**Quick Order**) and "Manage" (**My Orders**, **Favorite Shops**) — no Bazaar-side "post a problem"-style broadcast entry was added, since none was requested; it's a natural future addition ("ask nearby shops for a hard-to-find item") if wanted later. None of these destinations exist yet (Worker/Business module remainders — Pending Modules 4/5), so every item opens a full-screen `ComingSoonModal` (`components/ComingSoonModal.tsx` — the same chrome as `NearbySearchModal`, minus the search bar: gradient header with a `chevron-left` back button, a centered icon + "Coming Soon" title + a per-item bespoke message) instead of a transient toast — per follow-up feedback that tapping a drawer item should feel like opening a real (if not-yet-built) screen, matching how "Nearby Workers"/"Nearby Shops" already behave, not a fire-and-forget toast.

**Each `DrawerMenuItem` in these two drawers gets its own distinct, colorful gradient, not one repeated color** — per follow-up feedback that every icon square looking the same (all brand blue) read poorly. Both drawers define the same small local palette (`BLUE_GRADIENT` = `headerGradient`, `GREEN_GRADIENT` = `['#16A34A', '#4ADE80']`, `PINK_GRADIENT` = `['#DB2777', '#F472B6']`, plus `PURPLE_GRADIENT` = `['#7C3AED', '#A78BFA']` in `ServicesMenuDrawer` only, for "Post a Problem") and assign one per item by role, reused consistently across both tabs: blue for the "quick action" item (Quick Book/Quick Order), green for tracking (My Bookings/My Orders), pink for favorites (Favorite Workers/Favorite Shops). Deliberately **no orange/amber anywhere in this palette** — `colors.secondary`/`colors.warning` (i.e. `SHOP_GRADIENT`) stays reserved for the Business capability identity only, per the explicit instruction (originally given for `NearbySearchModal`, applied here too) not to introduce that color into any menu/search surface without being asked. Each item's chosen gradient carries through to the `ComingSoonModal` it opens (icon, icon-backdrop tint, and would-be accent color all derive from the same `gradient` prop), so the color identity established in the drawer row doesn't reset once the screen opens.

**Bazaar's tab chrome (header + its menu drawer) uses the constant brand blue, matching every other tab — orange stays only on `BusinessProfileCard`/`BusinessProfileModal`.** `GradientHeader` takes an optional `gradient` prop (defaulting to the constant brand-blue `headerGradient`) — `BazaarHeader` originally passed `SHOP_GRADIENT` (imported from `BusinessProfileModal`) here and to its menu, so Bazaar's top chrome matched the orange identity established for Business elsewhere. Per follow-up feedback ("the header and its menu too"), `BazaarHeader` no longer passes a `gradient` override to `GradientHeader` at all (falls through to the default `headerGradient`) and `BazaarMenuDrawer` is hardcoded to `headerGradient`, never `SHOP_GRADIENT` — `SHOP_GRADIENT` is not imported into either file. `SHOP_GRADIENT` remains exported from `BusinessProfileModal` and used only by `BusinessProfileCard`/`BusinessProfileModal` themselves, which represent the *Business capability* identity (reachable from Home's menu and Profile too, not just the Bazaar tab) rather than "the Bazaar tab's own chrome" — capability-identity color stays orange everywhere it appears; tab-chrome color (header, menu, tab bar) is uniformly blue across all tabs including Bazaar. (Separately, `NearbySearchModal` — opened from Home's menu, not Services/Bazaar's — was corrected the same way for the same reason: always `headerGradient`, never `SHOP_GRADIENT`, per explicit instruction not to reintroduce that color there without being asked.)

**The bottom tab bar is a floating pill card whose active-tab dot lives inside the bar, just below its icon — not floating above the bar the way an earlier version of this component had it, not `@react-navigation/bottom-tabs`' default rendering either** — `CustomTabBar` (`components/CustomTabBar.tsx`) is passed via `Tab.Navigator`'s `tabBar` prop (`AppNavigator.tsx`). This is a full replacement of every earlier design of this component (a concave SVG notch with an overlapping bubble, an iOS-glass blurred pill with a sliding icon+label capsule, a version of this same pill design with the dot floating above the bar instead of inside it) — none of those are iterated on or reused. `position: 'absolute'` on the outer wrapper keeps it contributing ~0 height to `BottomTabView`'s flex layout, so screens render full-height and scroll behind the floating bar, same rationale as every earlier version. The bar itself (`styles.bar`) is a `colors.surface` pill (`BAR_RADIUS = BAR_HEIGHT / 2`, `BAR_HEIGHT = 66` — taller than earlier versions specifically to give the icon+dot stack room) with margin on every side and a plain platform shadow (`elevation` on Android, `shadowOffset`/`shadowOpacity` on iOS) — no blur, deliberately: `expo-blur`'s Android blur method needed several fix passes in an earlier iteration and was dropped entirely along with the glass design it supported. `paddingHorizontal: BAR_PADDING_H` (5) on the bar itself keeps the first/last tab's content a small, deliberate distance in from the bar's own rounded edge. This design is icon-only — no tab labels — matching every prior version's decision. It floats by the same amount on every side: `MARGIN_H` insets the bar from the left/right screen edges, and `barBottom = Math.max(insets.bottom, MARGIN_H)` keeps the bottom gap at least `MARGIN_H` too (growing beyond it only if the device's own safe-area inset genuinely needs more clearance than that) — `wrapper`'s `justifyContent: 'flex-end'` is what makes this margin actually reach the screen; several earlier rounds of "still too much gap" reports turned out to be about `wrapper` never bottom-aligning its (taller, at the time, to reserve room for the since-removed above-bar dot) content at all, not about `barBottom`'s value.

**Each tab stacks its own dot directly below its own icon, inside `tabContent` (a plain centered column), rather than one dot sliding between tabs** — moving the dot inside the bar removed the need for it to travel horizontally to whichever tab is active (an earlier version's `dotX`/`Animated.spring`/`translateX` slide, plus a `dotOuter` positioned above the bar with an Android-only `glowRing` to fake a colored glow that plain `elevation` can't produce) entirely: with one dot living permanently under each tab's own icon, all that's left is fading it in/out with that tab's own `progress` value, the same one already driving the icon crossfade. `dotShadowWrap` (`DOT_SIZE = 6`) wraps a `LinearGradient`-filled circle in that tab's own gradient color, with a real tinted iOS shadow (`shadowColor` set inline) and a plain `elevation` on Android (no glow-ring fake needed now — the dot's small, contained size next to its icon doesn't call for the same emphasis the old floating dot did).

**Every tab's icon sits at the bar's true vertical center at rest; only the selected tab's icon lifts up on selection, revealing its dot below it — the dot is never allowed to permanently reserve layout space that would push icons off-center.** An initial version of this "dot below the icon" layout gave `dotShadowWrap` a `marginTop` inside the same normal-flow column as `iconArea` — since the dot is always present in the tree (only its `opacity` animates, so unselected tabs render it invisibly, not unmounted), that `marginTop` was *always* reserved, on every tab, shifting every icon up from the bar's true center uniformly — which is what actually broke "all icons vertically centered," not any per-tab inconsistency. The fix: `dotShadowWrap` is `position: 'absolute'` (`top: ICON_BG_SIZE + DOT_MARGIN_TOP`, `DOT_MARGIN_TOP` trimmed 4 → 2 → 1 → 0.5 → 0 across follow-up feedback to tighten the icon-to-dot gap, then to `-2` per a final request to move the dot up slightly past flush (a small deliberate overlap into the icon's own backdrop box, not visually into the icon glyph itself), anchored against `tabContent`'s own box) rather than a flow-affecting margin, so `tabContent`'s size — and therefore `iconArea`'s centered position within `tabButton` — is driven by `iconArea` alone. `iconArea` itself is now the `Animated.View` carrying a `translateY` (`iconLift`, `progress`-driven, `0 → -6`) — since `transform` is a paint-time effect that never affects an element's own layout box, animating it doesn't disturb the centering math above: at rest (`progress = 0`) the icon sits exactly where `tabContent`'s centering places it (the bar's true vertical center), and only on selection does it visibly rise, opening up the gap to its dot below (which stays anchored to the icon's *resting*, not lifted, position, so the gap is what visibly grows).

**Per-tab icons cross-fade between muted and brand-colored, plus a soft tinted circle that visibly pops larger behind the active one, all driven by `Animated.Value`s on the native (UI) thread** — `progressAnims[index]` runs `0 → 1` via `Animated.timing` (260ms, `easing: Easing.out(Easing.cubic)`, `useNativeDriver: true`) whenever that tab becomes/stops being active; an earlier pass left this on the JS driver (`useNativeDriver: false`, out of an abundance of caution around color interpolation that these values don't actually do), which is what read as not-quite-smooth — every value this drives is opacity/transform only, so native-driving it was safe and is what actually fixed the jank. Rather than animating a vector-icon component's `color` prop directly (unreliable — `FontAwesome6` is a composite component wrapping an internal glyph, not a plain host view, so there's no guarantee `Animated.createAnimatedComponent` can push prop updates through it), each tab renders **two** plain, statically-colored icons stacked in the same box and cross-fades their wrapping `Animated.View`s' `opacity` — a muted-color one fading out (`Animated.subtract(1, progress)`) and a gradient-colored one fading in (`progress` directly), the same "stack two versions, cross-fade via opacity on a wrapping Animated.View" technique earlier versions of this component used for SVG notch paths. `iconBg` (`ICON_BG_SIZE = 40` — brought back down from an earlier 52 now that it has to share the bar's vertical space with the dot below it rather than owning the bar's full height alone — a circle tinted `${gradient[0]}1A`, a light alpha wash matching `LocationPicker`'s own detect-button tint convention, sized and positioned to exactly fill `iconArea`) fades/scales in behind the icon on the same `progress` value. The earlier `lift` (`translateY`, reaching the icon/backdrop up toward a dot that floated above them) is gone entirely along with that dot — with the dot now below the icon instead, there's nothing above to reach toward, so both views now animate scale only. A separate, shared `popScale` value (reset to `0.7`, sprung back to `1` with `friction: 5`/`tension: 180` — underdamped enough to overshoot slightly past `1` before settling) is stacked as an *additional* `scale` transform on `iconBg` and the dot, so the selected tab's backdrop and dot both visibly grow a little larger than their resting size on selection instead of just linearly scaling up — applied unconditionally to every tab (harmless on the others, since their opacity is fading toward `0` regardless). Deliberately not applied to the icon glyph itself (`iconScale`, capped at a modest `1.08`) — an earlier version stacked `popScale` onto the icon too, and the icon's overshoot could momentarily outgrow its own backdrop circle during the spring, reading as the icon poking out past its background. Keeping the pop off the icon guarantees it stays visually contained at every point in the animation, not just at rest.

**Per-tab colors are a `LinearGradient` tuple, not a flat color** — `ACTIVE_GRADIENTS` maps each route name to a two-stop gradient; every tab, including Bazaar, resolves to the constant brand-blue `headerGradient` (this doc previously said Bazaar resolved to its own `SHOP_GRADIENT` here — stale, from before the "Bazaar's tab chrome now uses the constant brand blue" fix described above; `SHOP_GRADIENT` stays reserved for `BusinessProfileCard`/`BusinessProfileModal`'s capability identity only, never tab chrome) — same mapping (renamed from the earlier bubble/capsule designs' own gradient maps) every prior version of this component has used.

**Toasts, not `Alert.alert`, for every app-surfaced message** — `Alert.alert` is a native OS dialog: blocking, modal, and visually inconsistent with the rest of this app's design language. Replaced everywhere (profile-creation success, permission-denied, GPS-detect-failure, post-registration pointer) with `showToast({ variant, title, message })` (`state/toastStore.ts`, a plain zustand store holding at most one active `ToastMessage` — a new one replaces whatever's showing, matching `Alert`'s own one-at-a-time behavior, no queue needed for this app's usage). `components/ToastHost.tsx` is mounted once at the root in `App.tsx` (a sibling of `RootNavigator`, same pattern as `LogoutOverlay`) and renders whatever `toastStore.toast` currently holds: a floating card below the safe-area top inset, gradient icon circle keyed by `variant` (`success`/`error`/`info` — success green, the same red as `LogoutConfirmModal`, and brand blue respectively) plus a matching left accent bar, sliding down/fading in via `Animated.timing` (not `spring` — same rationale as the drawer animation elsewhere in this doc) and auto-dismissing after ~3.2s, or immediately on tap. `showToast()` is a plain exported function (not a hook) specifically so it can be called from `onSuccess`/`onError` mutation callbacks and other non-component code, the same call sites `Alert.alert` used to occupy.

**Language, Theme, and Logout share dedicated modals across both menus**: `LanguagePickerModal` and `ThemePickerModal` (centered cards — gradient header, selectable option rows with a per-option gradient icon and a checkmark on the active one; `LanguagePickerModal` mirrors `ThemePickerModal`'s structure exactly) replace inline switcher pill rows in both `HomeMenuModal` and `ProfileMenuModal` — each now shows Language/Theme as a tappable row (icon, label, current value, chevron) instead. `LogoutConfirmModal` (centered card, red gradient icon circle, title/message, Cancel + red-gradient Logout buttons) gates the actual `useLogout()` call behind an explicit confirmation in both menus; the Logout trigger itself is a distinct red gradient (`#ef4444` → `#dc2626`) — a deliberate, intentional exception to the "every primary button uses the brand gradient" rule below, reserved for this one destructive action. `state/themeStore.ts` exports `themeModeLabelKey(mode)` and `state/settingsStore.ts` exports `languageLabelKey(language)` so both menus resolve the same "current value" label without duplicating the mapping.

**`ProfileMenuModal`, `ThemePickerModal`, and `LogoutConfirmModal` use the platform `Modal`'s built-in `animationType="fade"` plus `statusBarTranslucent`** — no custom `Animated`-driven transition, since none of them need a directional effect the built-in type can't express. **`HomeMenuModal` is the one exception**: it's a genuine slide-in drawer (per its reference design), which `animationType` has no built-in equivalent for, so it drives its own `Animated.timing` on `translateX`/backdrop opacity — but deliberately `timing`, not `spring`, for both open *and* close. The very first version of this drawer used a `spring` for its close animation; a spring has no fixed duration (it runs until it settles within a threshold, which can take an unpredictable extra beat), and since the native `Modal` stays mounted — and keeps swallowing all touches, including the header's own menu button — until that animation reports `finished`, an unpredictable spring-close made reopening the drawer right after closing intermittently feel broken. A fixed-duration `timing` (with `Easing.out(Easing.cubic)` for the deceleration feel) keeps the slide smooth while guaranteeing the Modal frees up input again after the same short, known window every time. Any new modal in this app should default to the platform's own `animationType`/`statusBarTranslucent`; reach for a custom `Animated` transition only when there's a concrete directional-motion requirement the built-in types can't express, and prefer `timing` over `spring` for anything that also needs to unblock touches promptly on close.

**Loading affordances all use one shared motif — dots orbiting a center point (`LoadingIndicator`)** — instead of the platform's generic `ActivityIndicator`. `LoadingIndicator` (`size`/`color`/`dotSize`/`duration` props) is what `Button`'s `loading` state renders, so every submit button in the app (Register/Login/Otp, etc.) picks it up automatically. **Logout gets a dedicated full-screen variant**: `authStore.isLoggingOut` (set in `useLogout()`'s `onMutate`, cleared in `onSettled` — after `clearSession()`, so `RootNavigator` has already swapped to the Auth stack by the time the overlay starts fading) drives `LogoutOverlay`, rendered from `App.tsx` as a sibling of `RootNavigator` so it draws above whichever navigator is mounted regardless of the swap happening underneath it. `isLoggingOut` is deliberately excluded from `authStore`'s persistence (`partialize`) — a stuck `true` surviving an app kill mid-request would otherwise show the overlay forever on next launch. `LogoutOverlay` composes a large `LoadingIndicator` (`size={96}`, `duration={1800}` — slower than the default 900ms, since a bigger ring spinning at the same speed reads as frantic) plus a pulsing center mark unique to this full-screen variant — logging out is the one transition where the whole screen is about to change underneath the user, so it earns its own full-screen beat rather than just a bigger version of the inline spinner alone.

**`WelcomeScreen`** (the Auth stack's entry point, and where logout always lands) is a full landing screen, not a bare button stack: a gradient hero panel (`headerGradient`, the same treatment `GradientHeader` uses — brand icon, app name, tagline) followed by a single "Create Account" `Button` and a plain text "Already have an account? Log In" link. It's deliberately **not** a role picker — every self-registered account is a plain `user` (see Account Model below), so there's no role choice to make here; an earlier version had three role-selection cards (Customer/Worker/Business) before that model was settled. It intentionally does **not** use the shared `ScreenContainer` (which applies a fixed `padding: 20` on all sides) — the hero panel needs to bleed edge-to-edge and up under the status bar the way `GradientHeader` does, so the screen composes its own `SafeAreaView`s directly instead.

**Icons**: `FontAwesome6` (`@expo/vector-icons`), not Ionicons — the free tier's icon set is mostly solid-only (no outline counterpart for `home`/`magnifying-glass`/`store`/`bars`/`arrow-left`/`screwdriver-wrench`). Solid vs. regular style is selected via a boolean prop (`solid`) matching the style name, same mechanism FA5 used — not an `iconStyle` string prop, despite an internal `FA6Style` const suggesting otherwise. Migrated from FA5 solely to get the `screwdriver-wrench` glyph (Services tab); FA6 also renamed a couple of glyphs used elsewhere in the app (`search` → `magnifying-glass`, `times` → `xmark`). `CustomTabBar`'s own icon/backdrop/glow-dot treatment (see above) is this app's one deliberate exception to "no background pill or per-icon glow" — it's the primary way active-tab state reads, not decoration; any *other* new tab or header icon should stay plain color-only unless it specifically needs its own active-state indicator. Follow the same icon family for any new tab/header icon regardless.

**Buttons**: the shared `Button` component and the active pill in `LanguageSwitcher`/`ThemePickerModal` all render the brand gradient as their background (via `LinearGradient`, since a `Pressable`/View can't have a gradient `backgroundColor` directly) — never a flat `colors.primary` fill. Any new primary-action control should follow this pattern for visual consistency. The one deliberate exception is Logout (`HomeMenuModal`/`ProfileMenuModal`'s trigger and `LogoutConfirmModal`'s confirm button), which uses a distinct red gradient (`#ef4444` → `#dc2626`) instead — a destructive/exit action, not a primary one, so it's intentionally visually distinct rather than blending in with every other button in the app. `Button` takes an optional `gradient` prop (defaulting to `headerGradient`) precisely so a screen with its own brand-distinct gradient header can keep its submit button visually consistent with that header instead of the app-wide blue — `BusinessProfileModal` passes its orange `SHOP_GRADIENT` (`#F59E0B` → `#D97706`, matching its own header) rather than introducing a separate flat-orange button style.

**Light/dark theme**: only `background`/`surface`/`text`/`textMuted`/`border` vary between `lightColors` and `darkColors` (`theme/colors.ts`, currently `#F9FCFF`/`#0c0f14` background/text swapped between the two) — brand colors (primary, secondary, success/warning/error, the header gradient) stay constant in both. Any component that renders one of the theme-dependent keys must read it from `useThemeColors()` inside the component body (so it re-renders on theme change), never from the static `colors` export — `StyleSheet.create()` at module scope can't be reactive, so theme-dependent values are applied via inline `style={[...]}` overrides, not baked into the stylesheet. `themeStore` only persists the user's choice (`system`/`light`/`dark`); `useThemeColors()` resolves `system` against the device's live scheme on every render.

`RootNavigator.tsx` also passes a `theme` to `<NavigationContainer>` built from `useThemeColors()` (based on React Navigation's own `DefaultTheme`/`DarkTheme`) — without this, React Navigation's hardcoded default (light) background shows through anywhere screen content doesn't fully cover it. Any future navigator added at the root level inherits this automatically; don't reintroduce a bare `<NavigationContainer>` without the `theme` prop.

**Status bar**: `App.tsx`'s `<StatusBar style="light" />` is hardcoded, not theme-reactive — every screen's persistent top chrome is the blue gradient header, so the status bar overlaying it needs light text/icons in both light and dark mode. Don't switch this back to `"auto"` without also removing/reworking the gradient header, since `"auto"` would make status bar text unreadable against the gradient whenever the in-app theme is light.

**Native chrome outside the React tree**: Android's edge-to-edge system navigation bar (and the native root window background it reveals) isn't part of the component tree at all — no amount of in-app `View`/`StyleSheet` styling reaches it. `App.tsx` syncs it explicitly on every theme change: `expo-system-ui`'s `SystemUI.setBackgroundColorAsync(colors.surface)` (root window background — this is what a mismatched `NavigationContainer` theme was actually leaking through, not an Android rendering bug in the tab bar itself) and `expo-navigation-bar`'s `NavigationBar.setStyle(...)` (Android-only, nav bar icon color). Synced to `colors.surface`, not `colors.background` — the system back/home/recents bar sits directly below `CustomTabBar`, which is itself `colors.surface`, so using `colors.background` there left a visible seam where the two met; `expo-navigation-bar` 57.0.1 has no `setBackgroundColorAsync` of its own (Android enforces edge-to-edge now, so the nav bar itself is always transparent) — `SystemUI`'s root-window-background call is the only mechanism that reaches this area. Also: `app.json`'s `userInterfaceStyle` must stay `"automatic"`, not `"light"` — that setting locks the *native* Android appearance independent of `themeStore`'s in-app choice, which directly undermines the dark mode feature if ever changed back.

**`LocationPicker`** (`user-app/src/components/LocationPicker.tsx`) is "Use my current location" (`expo-location`'s `requestForegroundPermissionsAsync` → `getCurrentPositionAsync` → `reverseGeocodeAsync`, building a display address from `name`/`city`/`region`) with a manual `TextField` fallback. There's no map/pin-drop UI yet, so manual entry only ever produces an address string — `latitude`/`longitude` stay `null` until GPS actually succeeds; editing the address text after a successful GPS detect clears the coordinates too, since the text no longer necessarily matches them. **Used only by `RegisterScreen`'s account-level registration location now** — `WorkerProfileModal`/`BusinessProfileModal` moved to `AddressPicker` (below) once a single free-text field was found not precise enough for a Worker/Business capability's location. Takes an optional `accentColor` prop (defaulting to `colors.primary`) for its "use current location" button's border/tint/icon color — the same rationale `AddressPicker` inherits, below.

**`AddressPicker`** (`user-app/src/components/AddressPicker.tsx`, and an identical copy at `partner-app/src/components/AddressPicker.tsx` — same "no shared package" duplication as everything else cross-app) replaced `LocationPicker` for Worker/Business profile forms per explicit product decision: `city`/`district`/`state`/`pincode` (required, `pincode` restricted to 6 digits client-side too) plus an optional `area` (street/locality/landmark). "Use my current location" still reverse-geocodes via the same `expo-location` calls `LocationPicker` uses, pre-filling whatever fields it can (`place.city ?? place.subregion` → city, `place.subregion ?? place.district` → district, `place.region` → state, `place.postalCode` → pincode, `place.street ?? place.name` → area) — but unlike `LocationPicker`, editing a text field afterward does **not** clear the detected `latitude`/`longitude`, since fixing a typo in one field doesn't invalidate an otherwise-correct GPS fix. `WorkerProfileModal`/`BusinessProfileModal` (and their `partner-app` equivalents, `WorkerRegistrationScreen`/`BusinessRegistrationScreen`) hold an `AddressValue` (`{ latitude, longitude, area, city, district, state, pincode }`, default `EMPTY_ADDRESS`) instead of a `LocationValue`, and every place that used to display `profile.locationAddress` (`WorkerProfileCard`/`BusinessProfileCard`, `partner-app`'s `MyInfoScreen`, `admin-web`'s profile detail page) now calls a small `formatAddress()` util (`user-app`/`partner-app`/`admin-web` each have their own copy, e.g. `user-app/src/utils/formatAddress.ts`) that joins the parts into "Area, City, District, State - Pincode". `registration-web` has the same fields via its own `AddressField` component — no reverse-geocoding available there (same limitation the old `LocationField` had), so "capture my location" only grabs `latitude`/`longitude` in the background and every text field stays manual. See `.cloud/project-context.md`'s migration `0008` note for the backend/schema side of this change.

**State and District are dropdowns constrained to India's real states/districts, not free text** — per explicit follow-up feedback. `constants/indiaLocations.ts` (a plain data file, duplicated across `user-app`/`partner-app`/`registration-web` — same "no shared package" convention as everything else cross-app) exports `INDIA_STATES: string[]` (all 28 states + 8 union territories) and `INDIA_DISTRICTS_BY_STATE: Record<string, string[]>`; the file's own doc comment flags it as a point-in-time snapshot that should be re-verified against an authoritative source before relying on it beyond a form picklist, since district boundaries are periodically revised by state governments. District options are **cascading** — filtered to whichever state is currently selected (`INDIA_DISTRICTS_BY_STATE[state] ?? []`), and picking a new state clears the current district selection unless it's still valid for the new state (`AddressPicker`'s/`AddressField`'s own `handleStateChange`). In the mobile apps, a new shared `components/SelectField.tsx` renders a `TextField`-styled tap target that opens a full-screen searchable list (`SelectModal`, defined in the same file) — same chrome convention as `NearbySearchModal` (gradient header, search bar in its own card below the header, `FlatList` body) rather than a fourth distinct modal style; `District`'s `SelectField` is `disabled` (with a "Select a State first" hint) until a state is chosen. `registration-web`'s `AddressField` uses plain `<select>`/`<option>` elements instead, styled via a new `.field select` rule in `global.css` (matching `.field input`'s existing border/radius/padding, plus a dimmed `:disabled` state) — simpler than porting a custom searchable-list component to the web, and a native `<select>` already has adequate built-in type-to-search behavior in every major browser. GPS reverse-geocoding on `AddressPicker` now only auto-fills State/District when the geocoded name actually **matches an entry in the fixed list** (`matchInList()`, a case-insensitive lookup returning the list's own canonical spelling) — a name that doesn't match anything (a real possibility, since `expo-location`'s geocoder and this hand-maintained list don't share a common source of truth) is left for manual dropdown selection rather than silently storing an unlisted value in what's now a controlled field; `registration-web`'s `AddressField` never had reverse-geocoding to begin with, so this only applies to the mobile apps. `admin-web` needed no change here — it only displays the already-submitted address (via `formatAddress()`), never edits one.

**`matchInList()`'s exact-match rule was too strict in practice — reported as "District isn't auto-selecting."** Reverse-geocoder output frequently doesn't line up byte-for-byte with this hand-maintained district list (a "District" suffix, different spacing, or district-level info landing in `subregion` vs `district` vs `city` depending on OS/geocoder version), so an exact case-insensitive match often silently found nothing. Fixed in `AddressPicker` (both copies): `normalize()` now strips a trailing "district" word and collapses whitespace before comparing, `matchInList()` falls back to substring containment (either direction) when the normalized exact match fails, `handleDetect` tries `place.subregion`, then `place.district`, then `place.city` as candidate sources in turn instead of committing to one, and — when District genuinely still can't be matched — a toast tells the user to select it manually instead of leaving an unexplained blank field. `registration-web`'s `AddressField` has no reverse-geocoding at all, so none of this applies there.

**`ImagePickerField`** (`user-app/src/components/ImagePickerField.tsx`) follows the pick-then-upload-on-submit flow proven in a sibling project: `expo-image-picker`'s `requestMediaLibraryPermissionsAsync` → `launchImageLibraryAsync` (gallery only, no camera) holds picked images as local URIs in component state for preview; the actual multipart upload only happens when the surrounding form is submitted (`workersService`/`businessesService` build a `FormData` with `{uri, name, type}` file objects — the shape React Native's networking layer expects for a file entry, not a real `Blob`). `apiClient.postForm()`/`patchForm()` are the two places that send a `FormData` body instead of JSON — `Content-Type` is explicitly `multipart/form-data` with no boundary; React Native's networking layer fills the boundary in itself when it sees that exact header paired with a FormData body.

**`apiClient.ts` is built on `axios`, not React Native's built-in `fetch`** — matches the networking approach already proven reliable in a sibling project (CampuSphere's `CreateStudent` photo upload), adopted after `fetch`-based multipart uploads proved unreliable for Worker/Business photos in this Expo/RN version despite several targeted fixes (token-refresh retry, multer error handling, MIME-type inference) not resolving it. In React Native, `axios` resolves to the `XMLHttpRequest`-based adapter — a genuinely separate native networking code path from `fetch`, which has its own history of RN-version-specific quirks around multipart bodies. The `axios.create()` instance (`baseURL`, 45s `timeout`) is module-scoped in `apiClient.ts`; every method (`get`/`post`/`patch`/`delete`/`postForm`/`patchForm`) routes through it, so the public interface every service file (`authService`/`workersService`/`businessesService`) calls never changed. Any future networking change should stay on this same axios instance rather than reintroducing `fetch` anywhere in the app.

**Token refresh is single-flight, not per-request** — `apiClient.ts`'s `tryRefreshAccessToken()` shares one module-level `refreshPromise` across every concurrent caller instead of each 401'd request independently hitting `/auth/refresh`. This matters because refresh tokens rotate on use (single-use — the backend revokes the old one and issues a new pair on every refresh call, by design, for security): screens like Profile/Services/Bazaar all fire several authenticated queries in parallel on mount (worker profile, business profile, account info), so if the access token has expired, multiple requests can hit 401 within the same instant. Without dedup, each would call `/auth/refresh` with the same still-valid-looking refresh token — only the first to reach the server wins (its call rotates the token), and every other concurrent refresh attempt gets its own 401 (using an already-revoked token), which used to `clearSession()` and silently log the user out mid-flow. Any future authenticated-request helper (a new `apiClient` method, a websocket reconnect, etc.) must route through this same shared `tryRefreshAccessToken()` rather than rolling its own refresh call, or the race reopens.

**Token refresh also happens proactively, not just reactively on a 401** — `ensureFreshAccessToken()` decodes the access token's own `exp` claim (a small dependency-free base64url decoder, `base64UrlDecode()`, since RN/Hermes doesn't reliably provide global `atob`) and refreshes ahead of time if it's within 20s of expiring, called at the top of both `request()` and `requestForm()` before the request is built. This matters specifically for multipart uploads: re-sending the *same* `FormData` instance a second time (the previous reactive-only retry-on-401 behavior) is not something React Native's networking layer reliably supports once a file part has already been handed off once — a request that goes out with an already-stale token could fail on its retry too, with a *different*, non-401 error that wasn't retried again, surfacing as an opaque failure on the first submit attempt while a manual second attempt (a fresh `FormData`, and a by-then-refreshed token) just worked. Proactive refresh means the common case (token simply expired mid-form-fill) never reaches the reactive-retry path at all — the FormData is only ever sent once, already carrying a fresh token.

## Frontend Structure (partner-app/)

A second, standalone React Native (Expo) app — **Triolo Partner** — for Worker/Business registration and login, added as an explicit product decision (see "Cold-start supply" below) rather than folded into `user-app` as another optional flow. Same backend, same account model as `user-app`'s (a phone number registered here is the *same account*, just reached capability-first) — but a genuinely separate Expo project, not a monorepo package: this repo has no root `package.json`/workspace tooling (`user-app`/`backend` are plain sibling folders), so `partner-app` follows that same pattern rather than introducing workspace infrastructure just for this. That means no direct code import between the two apps — `partner-app` re-implements (copies, then adapts only what's genuinely Partner-specific) `user-app`'s already-proven `theme/`, `apiClient.ts`, `authStore`/`themeStore`/`settingsStore`/`toastStore`, `LocationPicker`/`ImagePickerField`/`GradientHeader`/`ConfirmModal`/`VerificationBadge`/`ToastHost`/`LogoutOverlay`, and the auth OTP screens verbatim, rather than sharing a package. **A fix or improvement to any of those in one app should be checked against the other** — there's no tooling that keeps them in sync automatically.

**Deliberately minimal for this first pass**: no first-launch language picker, no inline language switcher (`user-app` has both) — device locale still drives en/te via `i18n.ts`, and an account's saved `preferredLanguage` still overrides it on login (same `authStore.setSession` behavior). `MyInfoScreen` is **read-only** — no edit/delete yet, even though the backend `PATCH`/`DELETE .../me/profile` endpoints it would need already exist and are proven by `user-app`'s own `WorkerProfileModal`/`BusinessProfileModal`; wiring them here is a natural, low-risk follow-up, just not built until asked for.

**Business registration uses the same brand-blue gradient as everything else in this app, not the orange `SHOP_GRADIENT` `user-app` uses for its Business *capability* identity** (`BusinessProfileCard`/`BusinessProfileModal` — still deliberately orange there, unaffected by this) — `BusinessRegistrationScreen`'s chips/submit button/`AddressPicker` accent and `ChooseCapabilityScreen`'s Business card icon all resolve to `headerGradient` now, per explicit follow-up feedback that this app's registration surfaces should look uniform regardless of which capability is being registered.

**There is no standalone `RegisterScreen` in this app anymore — `WelcomeScreen` leads straight into one of two capability-specific, self-contained registration screens: `RegisterWorkerScreen` / `RegisterBusinessScreen`.** Per explicit instruction that registration should be "one place" (mirroring the same restructuring done to `registration-web` — see that section above), each screen combines Full Name + Mobile Number (via the shared `components/PhoneVerification.tsx`, with inline OTP verification) *and* that capability's own fields (skills/categories, experience or shop name, `AddressPicker`, photos, delivery) into a single scrollable form. Every field is fillable from the start; only the Submit button is gated on the mobile number being verified. `email` is not asked for anywhere in this app (the shared backend `POST /auth/register/request-otp` endpoint made it optional for exactly this reason — see `.cloud/project-context.md`'s Account Model section); `Account.email`/`AuthAccount.email` are typed `string | null` accordingly, and the one place this app displayed it unconditionally (`ProfileScreen`'s hero card) is guarded against it being absent.

**`WelcomeScreen`'s two entry points ask "Are You a Worker?" / "Do You Have a Shop?" via the same card layout `ChooseCapabilityScreen` already uses, not a plain button pair with different copy.** Per explicit follow-up feedback that the app's very first screen should ask the same way `registration-web`'s `LandingPage.tsx` does, `WelcomeScreen`'s two `Button`s (previously `auth.registerAsWorker`/`auth.registerAsBusiness`, generic "Register as a Worker"/"Register as a Business" labels) were replaced with `EntryCard` pressables — gradient icon square, title, subtitle, chevron — the same visual shape as `ChooseCapabilityScreen`'s own `CapabilityCard`. Rather than adding a second, duplicate pair of translation keys, both cards reuse the **existing** `chooseCapability.workerUnregisteredTitle`/`workerUnregisteredSubtitle`/`businessUnregisteredTitle`/`businessUnregisteredSubtitle` keys (already "Are You a Worker?"/"Register your skills to get discovered by customers nearby"/etc., byte-for-byte matching `registration-web`'s `LandingPage.tsx` wording, and already translated into Telugu) — `WelcomeScreen` and `ChooseCapabilityScreen`'s not-yet-registered cards are asking the visitor the exact same question, so there's one source of truth for that copy, not two kept in sync by hand. The old `auth.registerAsWorker`/`auth.registerAsBusiness` keys (en + te) were removed accordingly.

**Verifying the mobile number mid-form does not navigate away from the screen** — this is the part that needed real plumbing, not just UI. `PhoneVerification` calls `authService.requestLoginOtp`/`requestRegistrationOtp` then `verifyLoginOtp`/`verifyRegistrationOtp` directly (not through the `useAuthMutations` react-query hooks — the login-then-fallback-to-registration branching doesn't map cleanly onto one mutation), and on success calls `setSession()` — which sets `accessToken`, and would normally make `RootNavigator` instantly swap from `AuthNavigator` to `MainNavigator`, unmounting whichever screen just called it. To prevent that mid-form, `authStore` gained a new transient (unpersisted) flag, `isCompletingRegistration`: `RegisterWorkerScreen`/`RegisterBusinessScreen` set it `true` on mount and `false` either on unmount or once their own `createProfile` mutation succeeds, and `RootNavigator`'s swap condition became `accessToken && !isCompletingRegistration ? <MainNavigator /> : <AuthNavigator />`. So verifying mid-form quietly establishes the session in the background while the same screen keeps rendering; only submitting the actual Worker/Business profile (or backing out of the screen) lets the swap happen — landing on `ChooseCapabilityScreen`, which shows the freshly-created profile's Pending status exactly as it would have via the old multi-screen flow.

**Once verified, Full Name and Mobile Number stay visible (disabled) — they are not replaced by a bare confirmation line.** This was an explicit correction after an initial pass on `registration-web`'s equivalent component collapsed the two fields into a single "✓ Mobile number verified" sentence once done; both `PhoneVerification` components (this app's and `registration-web`'s) now keep the fields rendered throughout, just non-editable. The verification status itself is an **icon inside the Mobile Number input's own right edge, not text near the label** — a first pass put a "Verified" badge next to the label (`TextField`'s `labelRight` prop); per a further explicit correction ("verified badge should be green color tick mark in input right side not above verified text... if not verified then show in orange like pending icon"), `labelRight` was replaced with `rightIcon`, absolutely positioned inside the input on its right edge: a `FontAwesome6`/`FontAwesomeIcon` `circle-check` in `colors.success` (green) once `verified`, or a `clock` in `colors.warning` (orange) while it isn't — so the field always shows a status icon, not just once verification succeeds. `registration-web`'s `PhoneVerification` mirrors this exactly with a `position: relative` wrapper around the plain `<input>` and an absolutely-positioned `FontAwesomeIcon`.

**The "Verify"/"Verify Mobile Number" action itself sits beside the Mobile Number input, in the same row, not as a full-width button underneath it** — per further explicit follow-up feedback. This is a harder layout than it looks: `TextField` normally bundles its own label above the input as one block, so a naive sibling button next to a `TextField` centers relative to the whole label+input block, not the input alone, and visibly sits off-center from the input itself. The fix, applied everywhere this pattern is needed (see below), is to pull the label out and render it separately (as a plain `Text`/`<label>`) above a row containing a **label-less** `TextField`/bare `<input>` plus the sibling button, so `alignItems: 'center'`/`center` on the row has only two genuine, unencumbered siblings to align. `TextField` (both `user-app`'s and `partner-app`'s copies) gained two props for this: `label` became optional (omit it to render no label row at all) and a new `containerStyle` prop lets a caller zero out the default `marginBottom` so the row — not the field — owns its own spacing (an unzeroed margin on one sibling would otherwise make a plain `alignItems: 'center'` center against a taller invisible box and misalign anyway). The same fix applies to the "+ Add New" skill/category inline input (see below) — it has the identical shape (a bare input beside a "Done" button).

**Confirm OTP/Change Number (and any `Button`) render at a fixed height, not a height derived from their content** — `Button.tsx`'s `styles.button` (partner-app) switched from `paddingVertical: 14` to `height: 48`, and `registration-web`'s `.button` CSS class switched from `padding: 14px` to `height: 48px; padding: 0 20px`. Both values were chosen to match the prior padding-derived height almost exactly, so ordinary buttons look unchanged — but a fixed height means the button is the same size whether it's rendering its label `Text`/text node or a `LoadingIndicator`/`LoadingSpinner`, which otherwise have slightly different natural heights. This was reported as "Confirm and Cancel buttons' height not matching, while loading and normally" — adjacent buttons in `PhoneVerification`'s OTP row (only one of which is ever `loading` at a time) would visibly mismatch height whenever one was mid-request and the other wasn't.

**The "+ Add New" skill/category inline input has the same label-vs-sibling-button alignment problem as the Mobile Number/Verify-button pair above, and got the identical fix** — every place this pattern appears (`partner-app`'s `RegisterWorkerScreen`/`RegisterBusinessScreen`/`WorkerRegistrationScreen`/`BusinessRegistrationScreen`, `user-app`'s `WorkerProfileModal`/`BusinessProfileModal`, `registration-web`'s `CategoryChips`) previously passed the "What's your skill?"/"What's your category?" label through the inline `TextField`'s own `label` prop and tried to align the circular gradient "Done" button beside it via a `marginTop: 22` guess (an approximation of the label's height, imprecise across platforms/font metrics) inside an `alignItems: 'flex-start'` row. Fixed the same way: the label is now rendered separately (plain `Text`/`<label>`) above the row, the `TextField`/`<input>` inside the row carries no label of its own (`containerStyle={{marginBottom: 0}}` on the RN side; the web side just moved the `<label>` out of the flex row entirely, since `.field label`/`.field input` are descendant selectors and still style it correctly regardless of nesting depth), and the row itself switched to `alignItems: 'center'` — with no more marginTop guess needed, since both siblings are now plain, unencumbered boxes of comparable height.

**`OtpScreen`/`LoginScreen` are unaffected and still used for login** — only registration's OTP step moved inline. `AuthStackParamList`'s `Otp` route dropped its `mode` union down to just `{ mode: 'login'; mobileNumber: string }` (the `'registration'` value is no longer reachable from anywhere), and `useAuthMutations.ts` lost `useRequestRegistrationOtp`/`useVerifyRegistrationOtp` accordingly — `authService`'s underlying `requestRegistrationOtp`/`verifyRegistrationOtp` functions themselves are unchanged and still exported, just called directly by `PhoneVerification` instead of through a mutation hook.

**Once a Worker or Business capability's `verificationStatus` reaches `verified`, the app unlocks a real tab-bar shell** — `MainTabNavigator` (Home/Bookings/Earnings/Profile), using a direct port of `user-app`'s floating-pill `CustomTabBar` (`components/CustomTabBar.tsx`, ported per explicit follow-up feedback that this app's tab bar should match the main consumer app's rather than the plain default bottom-tabs bar it started with — see `user-app`'s own `CustomTabBar` doc comment for the full design rationale this inherits verbatim: the inline dot-below-icon, native-driven crossfade/pop animations, floating-margin-on-every-side layout). The one generalization from the port: `user-app`'s bar varies its active gradient per route (Bazaar gets its own orange); this app has no per-tab color identity — every tab, including registration, already resolved to the single brand-blue `headerGradient` — so `ACTIVE_GRADIENT` here is one constant, not a per-route map. **No shared package between the two apps' copies** — a fix or refinement to one should be checked against the other, same rule as every other duplicated component in this app (see the top of this section). `MainNavigator` decides its `initialRouteName` once, before mounting (`ChooseCapability` vs. `MainTabs`), from `useMyWorkerProfile()`/`useMyBusinessProfile()` — both hooks gained an optional `enabled` param for this.

**Bug fix**: `MainNavigator` originally gated only on `workerProfile.isLoading`/`businessProfile.isLoading` before deciding `hasVerifiedCapability`, with no `isError` check. TanStack Query's `isLoading` becomes `false` on a settled *error* just as much as a settled success — so a transient network/timeout failure on either profile query (retries exhausted) made `hasVerifiedCapability` compute `false` for a genuinely verified user, and `Stack.Navigator` locked in `initialRouteName="ChooseCapability"`. Since `initialRouteName` is a React Navigation prop read only once at that navigator's first mount, the user was stuck on `ChooseCapabilityScreen` — a single non-tab screen whose header shows a bare `right-from-bracket` logout icon, not the `bars` menu every real tab header has — until they killed and relaunched the app. This was reported as "sometimes opening the app shows only one tab, no tabs, and just a logout icon in the header," and is exactly that mechanism. Fixed two ways: (1) `MainNavigator` now renders a dedicated error view (title + message + a `Button` calling `refetch()` on whichever query errored) when either query is in `isError`, instead of silently falling through to `ChooseCapability`; (2) `Stack.Navigator` is now `key`ed on `hasVerifiedCapability`, so it remounts — and re-reads `initialRouteName` fresh — if that value legitimately changes within the same app session (a failed load recovering via retry, or a capability getting verified while the app happens to be open), rather than being permanently locked to whatever it first mounted with.

**A second, compounding bug was found and fixed in the same pass**: `authStore.ts`/`themeStore.ts`/`settingsStore.ts` (in **both** `user-app` and `partner-app` — identical copied code, see the "no shared package" note above) each set `isHydrated` inside their `onRehydrateStorage` callback by mutating the `state` object zustand hands back directly (`state.isHydrated = true`) instead of calling a `set()`-based action. A direct mutation like this bypasses zustand's `set()` entirely, so subscribers (`RootNavigator`'s `useAuthStore((s) => s.isHydrated)` / `useThemeStore(...)` / `useSettingsStore(...)`, which gate whether `RootNavigator` renders anything at all) aren't reliably or immediately notified — the new value only becomes visible whenever some unrelated later `set()` call on that same store happens to trigger a re-render. This is a second, independent source of "sometimes glitching" on cold start (RootNavigator's `return null` hydration gate resolving later/less predictably than it should). Fixed by adding a real `setHydrated: () => set({ isHydrated: true })` action to each of the three stores in both apps, and calling `state?.setHydrated()` from `onRehydrateStorage` instead of mutating `state` directly. Any future persisted store in either app should follow this pattern — mutate store state only through an action, never through `onRehydrateStorage`'s callback argument.

**Getting verified no longer requires a full app relaunch to notice.** After the fixes above, testing revealed `ChooseCapabilityScreen` genuinely showing correctly (registration cards / a Pending badge) for an account not yet approved in admin-web — expected behavior, not a bug — but with no way to see the change land short of fully killing and relaunching the app, since `useMyWorkerProfile()`/`useMyBusinessProfile()` only ever fetched once, on mount, with nothing to trigger a second fetch. Two additions fixed that: (1) `ChooseCapabilityScreen`'s `ScrollView` now has a `RefreshControl` (pull-to-refresh) calling `.refetch()` on both queries; (2) `App.tsx` (in **both** apps) wires React Native's `AppState` into TanStack Query's `focusManager` — `focusManager.setFocused(status === 'active')` on every `AppState` change — since React Query's `refetchOnWindowFocus` (on by default) relies on a browser `focus` event that doesn't exist in React Native, so without this wiring no query anywhere in either app was ever refetching on the app returning to the foreground, not just this screen's. Either trigger updates the same React Query cache entry (`WORKER_PROFILE_QUERY_KEY`/`BUSINESS_PROFILE_QUERY_KEY`) that `MainNavigator` itself reads, so its `key={hasVerifiedCapability ...}`-driven remount (see above) picks up a newly-verified status and switches to `MainTabs` without needing the app to be closed and reopened — background/foreground the app, or pull to refresh on `ChooseCapabilityScreen`, is now enough.

`MainTabs` lives as a screen inside the *same* stack as `ChooseCapability`/`WorkerRegistration`/`BusinessRegistration`/`MyInfo` rather than a second top-level navigator, so its `Profile` tab can push those same registration/detail screens on top of itself — e.g. a verified Worker without a Business profile yet sees an "Add your Shop" prompt card there that opens `BusinessRegistrationScreen` directly. Each tab's `GradientHeader` carries a `leadingIcon` matching its own tab icon (`house`/`calendar-check`/`wallet`/`user`) — the same "logo beside the title" treatment `ChooseCapabilityScreen`'s own header now also carries (`shapes`, the generic Triolo brand mark), so every top-level screen in this app shows a leading icon consistently.

**Every tab's header now carries a `bars` menu action opening `SettingsMenuModal`** (language/theme/logout), per explicit follow-up feedback that this app should get the same settings surface `user-app` has. `components/ThemePickerModal.tsx`/`LanguagePickerModal.tsx` are direct ports of `user-app`'s own (both work unmodified since `state/themeStore.ts`/`settingsStore.ts` were already copied verbatim); `SettingsMenuModal` is adapted from `user-app`'s `ProfileMenuModal` but shared across *every* tab (not Profile-only) since none of this app's tabs need distinct menu content the way `user-app`'s Home (onboarding entry points) differs from its Profile (settings only) — and it reuses this app's existing generic `ConfirmModal` for the logout confirmation rather than porting a dedicated `LogoutConfirmModal`, since `ConfirmModal` was already established as this app's one destructive-confirmation component. The menu-visibility state lives in `MainTabNavigator` itself (one `useState`, referenced from every tab's `screenOptions` header function) rather than four separate per-tab wrapper components, since the content is identical across tabs. `ProfileScreen`'s own body no longer has an inline logout button/`ConfirmModal` — matching `user-app`'s actual Profile screen, which also has no inline logout, only the menu's.

**`ProfileScreen` and `MyInfoScreen`'s hero cards had a padding-stacking bug**, per follow-up feedback that the gap above the card was much larger than its left/right gap: both screens' `body` style had its own `paddingVertical: 20` *in addition to* `ScreenContainer`'s own `flex` style, which already contributes a uniform 20px on every side regardless of the `edges` prop passed to it (`edges` only controls the `SafeAreaView`'s inset padding, not that base `padding: 20`). The extra vertical-only padding doubled the top gap without a matching horizontal equivalent. Fixed by dropping the redundant `paddingVertical` from both screens' `body` style — the top gap is now driven by `ScreenContainer`'s own uniform padding alone, matching left/right exactly.

**`MyInfoScreen` is no longer purely read-only** — a `pen` action in its own header (see below) opens `WorkerRegistrationScreen`/`BusinessRegistrationScreen` in edit mode with the already-fetched profile, per follow-up feedback ("profile can edit and add profile picture"). Both registration screens now double as edit forms, mirroring `user-app`'s `WorkerProfileModal`/`BusinessProfileModal` edit-mode branch field-for-field: an optional `route.params.profile` (`MainStackParamList`'s `WorkerRegistration`/`BusinessRegistration` routes now take `{ profile?: WorkerProfile }`/`{ profile?: BusinessProfile }`) switches `isEditMode` on, prefills every field via a `useEffect` keyed on the profile (photos become `PickedImage`-shaped entries from their remote URLs so `ImagePickerField` can show/remove them — "add profile picture" is this same flow: `ImagePickerField` already supports adding new photos alongside the existing ones), submits via `PATCH` (`useUpdateWorkerProfile`/`useUpdateBusinessProfile`, splitting photos back into `existingPhotoUrls` vs. newly-picked ones by `uri.startsWith('http')`) instead of `POST`, and adds a red "Delete" text action gated behind the existing generic `ConfirmModal` (`useDeleteWorkerProfile`/`useDeleteBusinessProfile`) — on success, `navigation.popToTop()` returns to whichever screen is first in the current stack (`ChooseCapability` pre-verification, `MainTabs` once verified — `initialRouteName` already picks the right one). `MyInfoScreen` itself switched from a navigator-level `header:` (which has no access to the fetched profile data the pen action needs) to rendering its own `GradientHeader` directly — the same wrapper-component pattern used everywhere else in this codebase a screen's header needs local data/state; `MainNavigator`'s `MyInfo` route is now `headerShown: false` accordingly, and its `WorkerRegistration`/`BusinessRegistration` routes' header titles switch to `workerProfile.editTitle`/`businessProfile.editTitle` when `route.params?.profile` is present.

**Header title sizing already matched `user-app` exactly** (`GradientHeader.tsx`'s `title` style — `fontSize: typography.heading.fontSize - 2`, semi-bold — and the underlying `typography.ts` tokens are byte-for-byte identical between the two apps, confirmed by diff) — no change was needed there, despite it being flagged in the same round of feedback as everything else in this section.

**Tab set is `Bookings`/`Earnings`, not a generic `Search`** — per explicit follow-up feedback to "show tabs that are necessary in future," a placeholder `Search` tab (whose purpose was never well-defined for a Worker/Business partner) was replaced with two tabs that map directly to already-documented future modules: `Bookings` (the booking/order-flow pipeline — Worker module remainder / Business module remainder, both still pending) and `Earnings` (the post-MVP worker earnings dashboard, `.cloud/roadmap.md`). Both are honest placeholders for now (`screens/main/BookingsScreen.tsx`/`EarningsScreen.tsx`), same pattern as `Home`; `Profile` is the one real tab — a gradient identity banner (avatar initials, name/mobile/email — see below), a summary card per capability (linking into the existing `MyInfoScreen` rather than duplicating its rendering), an add-the-missing-capability prompt, and logout.

**`ProfileScreen` and `MyInfoScreen` both use a shared "gradient hero card" identity treatment**, added per follow-up feedback asking for a more attractive info/profile presentation: a rounded `headerGradient` card with a translucent circular avatar (initials on `ProfileScreen`, since it represents the account; the capability's own icon on `MyInfoScreen`, since it represents that specific Worker/Business profile) and the name in white, with a real drop shadow (`shadowColor`/`shadowOffset`/`shadowOpacity`/`shadowRadius`/`elevation` — the same shadow convention `ToastHost` already established, extended to a `CARD_SHADOW` constant reused by every card on both screens, since flat 1px-bordered cards read as visually flat otherwise). `MyInfoScreen`'s previously-flat scroll of label/value rows is now grouped into a `DetailCard` (surface-colored, shadowed, rounded) with a `Divider` between sections, and each `InfoRow` gained a small tinted icon badge instead of a bare icon — the same "icon in a light tinted circle" treatment already used elsewhere in this app (e.g. `ChooseCapabilityScreen`'s capability cards). `ProfileScreen`'s capability cards gained a `quickFact` line (worker: years of experience; business: shop name) between the title and `VerificationBadge`, so the card conveys more than just a status pill at a glance.

**`ChooseCapabilityScreen`** is the app's home base (lands here after login/registration): fetches `GET /workers/me/profile` and `GET /businesses/me/profile` and renders one card per capability, styled after `user-app`'s `HomeMenuModal` entry-card pattern (gradient icon square, title/subtitle, chevron) — a capability that doesn't exist yet opens its registration screen on tap; one that does opens the read-only `MyInfoScreen` instead, showing its `VerificationBadge`. `WorkerRegistrationScreen`/`BusinessRegistrationScreen` are `user-app`'s `WorkerProfileModal`/`BusinessProfileModal` adapted from a `Modal` overlay into a plain navigator screen (create-only — the edit-mode branch, delete action, and their `ConfirmModal` wiring were dropped, not adapted) — same fields, same multi-select category chips + "+ Add New" pattern, same shared `LocationPicker`/`ImagePickerField`, same `POST .../me/profile` endpoints.

**Cold-start supply**: this app exists to solve the two-sided-marketplace bootstrap problem — requiring a Worker/shop-owner to install and navigate the full consumer app just to register was too much friction. The other half of that problem — reviewing/verifying what comes in, and reaching someone who won't install *any* app — is `registration-web/` + `admin-web/` (see below), built as a follow-up once the backend `admin` module existed to support it.

## Frontend Structure (registration-web/, admin-web/)

This project's first web frontends — Vite + React + TypeScript, plain CSS. **Two separate sites, not one** — an initial combined `web/` app (Admin dashboard + public registration forms together) was split into `registration-web/` (only ever `/`, `/worker`, `/business` — no admin anything, not even a link to it) and `admin-web/` (`/login`, `/`, `/workers/:id`, `/businesses/:id`) per explicit follow-up feedback, so the two audiences ship as genuinely independent deployments rather than routes on the same domain. **Why Vite, not Next.js**: neither site needs SSR/SEO — an internal tool and a handful of short-lived public forms — so the lower-setup-cost choice matches `docs/vision.md`'s "simple, lightweight, low-cost" MVP principle. No shared package between them, or with `user-app`/`partner-app` (same reasoning as `partner-app`'s own — no workspace tooling in this repo): `apiClient.ts`, `authStore.ts`, `errorMessages.ts`, `theme/tokens.ts`/`global.css` (the same `#0055D3`→`#1D76FA` gradient, Poppins via Google Fonts) are duplicated across both sites and kept in sync manually — flagged in both READMEs.

**`registration-web`'s vertical scrollbar is visually hidden, but scrolling itself is untouched** — `theme/global.css`'s `html` selector sets `scrollbar-width: none` (Firefox) / `-ms-overflow-style: none` (legacy Edge) plus an `html::-webkit-scrollbar { display: none }` rule (Chrome/Safari/Chromium Edge), per explicit request; nothing here sets `overflow: hidden` anywhere, so a taller page (the Worker/Business registration forms) still scrolls normally at the document level, just without a visible scrollbar track. `admin-web` was not touched — no such request was made for it, and its dashboard/detail pages don't share `registration-web`'s `global.css`.

**`apiClient.ts` is simpler than the mobile apps', not a copy** — a browser's `fetch`+`FormData` is safe to resend on retry (unlike React Native's, which is why the mobile apps' client proactively decodes the JWT and refreshes ahead of every request), so this one just does a plain reactive refresh-once-on-401. Session lives in `authStore`, a `localStorage`-persisted Zustand store (Zustand works identically outside React Native) — harmless for the public registration flow too, since it lets someone reopen their own registration link later and see their status.

**`PageHeader` is deliberately shorter than the mobile apps' `GradientHeader`, and website-only** — reduced vertical padding, no subtitle line at all (the mobile apps' header design is unchanged; this is a website-specific simplification, not a cross-platform one), and a back button (when given a `backTo` path) rendered *beside* the title in the same row, not stacked above it — as a circular translucent button (`header__iconButton`), mirroring the mobile apps' `GradientHeader` `iconButton` treatment rather than a bare icon with no background. A brand-mark logo badge (`header__logo`, a touch bigger than the back button, same proportion relationship as the mobile header's `leadingIconButton` vs. `iconButton`) sits beside the title too, using the same `shapes` FontAwesome glyph the mobile apps already use everywhere as their generic Triolo mark (`WelcomeScreen`, `HomeMenuModal`, `LogoutOverlay`). Icons are FontAwesome's via `@fortawesome/react-fontawesome` + `@fortawesome/free-solid-svg-icons` (both sites' first real icon-library dependency — the earlier combined `web/` app had none, using plain text/emoji glyphs instead). `PageHeader` is duplicated between the two sites like the rest of the shared infra above. `AdminDashboardPage` can't use `PageHeader` itself (it needs a right-side logout action `PageHeader` has no slot for) — its own inline header replicates the same logo badge + `header__iconButton` treatment by hand for visual consistency.

**`RequireAdmin` re-verifies `role` against `GET /auth/me` on every mount, not just the cached `account` in `localStorage`** — an account promoted to `admin` after a browser already logged in once (the ordinary case: `backend/scripts/seedAdmin.ts` only ever runs *before* someone's first login, so a manual DB promotion of an already-used account is the realistic path) would otherwise carry a stale `role: 'user'` snapshot indefinitely, since nothing previously re-checked it. Every admin data fetch (`AdminDashboardPage`'s list, `AdminProfileDetailPage`'s detail and its Approve/Reject `decide()`) also gained explicit `.catch` error handling and display — previously a failed request was indistinguishable from a genuinely empty list, since nothing surfaced the failure at all.

**The actual root cause behind "the dashboard loads but shows nothing" went one level deeper than `RequireAdmin`'s own fix above: the *access token itself* carries a stale `role`, and re-verifying via `/auth/me` doesn't change that.** `authenticate` (shared backend middleware) decodes `role` straight from the JWT payload — baked in at whichever login minted that specific token — and never re-queries `accounts` per request; `authorize('admin')` checks that decoded, potentially-stale value. So a token minted *before* a promotion keeps getting `403` from every `/admin/*` call forever, even though `/auth/me` (gated by `authenticate` alone, not `authorize('admin')`) correctly reads the account fresh and shows `role: 'admin'` — the mismatch is exactly what let `RequireAdmin` pass while every data call still failed. Confirmed `AuthService.refreshAccessToken` already re-reads the account from the database and signs the new pair from *that*, not the old payload — so `admin-web`'s `apiClient.ts` now retries once via the same single-flight `tryRefreshAccessToken()` on `403`, not just `401` (mirroring the mobile apps' own single-flight-refresh rationale for concurrent 401s). A single silent refresh mints a correctly-privileged token and the retried request succeeds, with no disruptive forced re-login; if the retry still `403`s, the account genuinely isn't `admin` and the error is left to surface normally.

**Every form step across both sites is a real `<form onSubmit>`, not a bare `<div>` with an `onClick` button** — `PhoneAuthFlow`, `AdminLoginPage`, and the Worker/Business registration forms all submit on Enter in any field, matching ordinary web-form expectations, with no per-input key handler needed (the browser's native form-submit-on-Enter behavior handles it). Every non-submit button inside these forms (`CategoryChips`' chips, `LocationField`'s detect button) is explicitly `type="button"` so it doesn't also trigger a submit on click. One thing to watch when adding a *new* Enter-handling input inside a form-wrapped section: `CategoryChips`' own "other category" text field already had its own Enter handler (to commit the typed tag) before this change — nesting it inside the page's own form meant that handler needed `e.preventDefault()` added, or Enter there would commit the tag *and* submit the outer form at the same time.

**`registration-web`'s `RegisterWorkerPage`/`RegisterBusinessPage` are single unified forms, not a separate auth screen followed by the actual registration form** — per explicit instruction that "registration should be one place": Full Name, Mobile Number, and every Worker/Business field (skills/categories, experience, address, photos, delivery) are all fillable together on one page from the start. The former `PhoneAuthFlow` component (a multi-step gate that had to fully complete, hiding the rest of the page, before a visitor could even see what they were registering for) was deleted and replaced by `PhoneVerification` (`components/PhoneVerification.tsx`) — a Full Name + Mobile Number block with an inline "Verify Mobile Number" button and an inline OTP field, rendered as part of the *same* form as everything else rather than gating it. It still tries `/auth/login/request-otp` first and falls through to `/auth/register/request-otp` (with the typed name) on `ACCOUNT_NOT_FOUND` — same "one flow covers both cases" logic `PhoneAuthFlow` used — but surfaces that inline instead of as its own screen. Only the page's **Submit button** is gated on verification (`disabled={!verified}`, with a caption explaining why while unverified) — the rest of the form is editable before, during, and after verifying, so filling in all the Worker/Business details first and verifying the mobile number last (as asked) works identically to verifying first. Once `PhoneVerification` calls back `onVerified()` (the OTP confirmed and `setSession()` already ran), the page checks whether that capability already exists on the account (`GET /workers|businesses/me/profile`) and shows its read-only status in place of the fillable fields if so — same logic as before, just triggered by the inline callback instead of a stage transition. The two pages otherwise still mirror `partner-app`'s `WorkerRegistrationScreen`/`BusinessRegistrationScreen` field-for-field (same category-chip + "+ Add New" pattern via `CategoryChips`) but with browser-native inputs: `PhotoUpload` (`<input type="file" multiple>`) instead of `expo-image-picker`, `AddressField` (structured State/District dropdowns + City/Area/Pincode fields, the browser Geolocation API for lat/lng only) instead of `expo-location` — no reverse-geocoding here, so "capture my location" only grabs raw coordinates in the background and every text/dropdown field stays manual.

**`LandingPage` is session-aware for a returning, already-registered visitor — it no longer keeps asking "Are You a Worker?"/"Do You Have a Shop?" once that capability already exists.** Per explicit follow-up feedback ("after registered then don't show again are you a worker/do you have a shop, instead show under-verification profile"), `LandingPage` now checks `authStore`'s persisted `accessToken` on mount and, if present, fetches both `workersService.getMyProfile()`/`businessesService.getMyProfile()` (each `.catch(() => null)`, matching the existing "no profile yet" convention `RegisterWorkerPage`/`RegisterBusinessPage` already used). Each capability's card swaps independently: a capability with no profile still shows the original registration prompt; one that already has a profile shows a "Your Worker/Business Profile" status card (a `VerificationBadge`) instead — mirroring the equivalent behavior `partner-app`'s `ChooseCapabilityScreen` already had. A logged-out visitor sees the original two prompt cards unchanged (nothing to check without a session). New `utils/formatAddress.ts` (a copy of `admin-web`'s own, same "no shared package" convention).

`RegisterWorkerPage`/`RegisterBusinessPage` got the matching other half of this fix: previously, `existingProfile` was only ever checked *after* `PhoneVerification`'s `onVerified()` fired — meaning a returning visitor who followed `LandingPage`'s new status-card link straight to `/worker`/`/business` would still have to re-enter an OTP just to see the same status they came from. Both pages now also run that same check proactively on mount (`useEffect` reading `useAuthStore.getState()`, calling the same `handleVerified()` used by the OTP flow) — a session already established gets the status view immediately, no redundant OTP. That status view itself was also expanded from a bare badge into a fuller detail block (skills/categories + experience or delivery pricing + `formatAddress()`'d location, in a `dl`) — "show all that info" once registered, not just a status pill, without introducing a "tabs" concept this site structurally has no equivalent for (unlike `partner-app`'s Bookings/Earnings/Profile tabs, which already unlock post-verification — see that section above; this site has no dashboard to unlock, just its own page's fuller status view).

**Bug fix (same change, found immediately after shipping the above)**: the first version of that mount-time `useEffect` only set `verified = true` when a persisted `accessToken` existed — it never populated the page's own `fullName`/`mobileNumber` state. Since `PhoneVerification` renders those two fields `disabled` once `verified` is true, and both pieces of state still started as empty strings, any visitor with *any* leftover session in `localStorage` (not just a genuinely already-registered one — a half-finished test session left over from earlier is enough) landed on a form whose Full Name/Mobile Number fields were both blank and disabled — reported as "name and mobile fields not able to select or focus at all," which is exactly what a blank disabled field looks like. Fixed by reading `account` off the same `useAuthStore.getState()` call and seeding `fullName`/`mobileNumber` from it before calling `handleVerified()`, so a legitimately-returning visitor sees their own name/number (correctly greyed out, not blank). `handleVerified`'s `catch` branch also now re-checks `useAuthStore.getState().accessToken` after the failed profile fetch — if `apiClient`'s reactive-refresh-on-401 ended up clearing the session entirely (an expired/invalid token whose refresh also failed), `verified` and both fields reset back to their normal empty/editable state instead of staying permanently stuck as "verified" against a session that no longer exists.

**`admin-web`'s `AdminLoginPage` is login-only** (no registration fallback, unlike `PhoneAuthFlow`) — `admin` accounts are provisioned via `backend/scripts/seedAdmin.ts`, never self-registered. Reuses the same `/auth/login/*` endpoints; rejects client-side if the returned account isn't `role: 'admin'` (the real enforcement is server-side `authorize('admin')` on every `/admin/*` backend route — this is only a friendlier message, per `docs/api-guidelines.md`'s "server-side, not just UI-hidden" rule). `RequireAdmin` gates every other route in this site the same way, redirecting to `/login` rather than rendering a broken dashboard for a logged-out or non-admin visitor.

**`AdminDashboardPage`** shows tabs (Workers/Businesses) × a verification-status filter (default `pending_verification`), each row linking to **`AdminProfileDetailPage`** — one component parameterized by a `capability` prop (mirrors `partner-app`'s `MyInfoScreen` dual-purpose pattern), with `AdminWorkerDetailPage`/`AdminBusinessDetailPage` as thin route-level wrappers supplying that prop. Approve/Reject calls `PATCH /admin/{workers|businesses}/:id/verification`. This page keeps its own inline header (not `PageHeader`) since it needs a right-side logout action `PageHeader` doesn't support — same "wrapper component for header-triggered local state" pattern the mobile apps' `HomeHeader`/`ProfileHeader` already established. `AdminProfileDetailPage` *does* use `PageHeader`, and briefly passed it `shop={capability === 'business'}` (turning Business detail pages orange) before that was found and removed as the same `shop`-prop mistake already fixed in `registration-web`/`partner-app` — Worker and Business detail pages render identically now. Both this page and `AdminDashboardPage`'s list rows also show `createdAt`/`updatedAt` (new `utils/formatDate.ts`) as plain informational text — "Registered `<date>`", plus "Last updated `<date>`"/"Edited `<date>`" when a profile has been edited since its original submission — since editing a profile no longer resets its verification status (see "Key Technical Decisions" in `.cloud/project-context.md`), this is purely FYI for the admin, not a re-review cue.

## Account Model

Every self-registered account is a plain `user` — not one of an exclusive set of roles chosen at registration. **Worker and Business are optional capabilities** a `user` account can add, either during onboarding (Home menu → "Are You a Worker?"/"Do You Have a Shop?") or, in principle, at any later point — not an exclusive choice made once at signup. Adding a capability creates a linked `worker_profiles`/`business_profiles` row (backend modules `workers`/`businesses`, each owning its own table per the module-boundary rule above) whose own `id` is that capability's distinct identifier (worker_id / business_id) and whose own `verification_status` (`pending_verification` → `verified`/`rejected`) gates admin trust for that capability specifically — independent of `accounts.status`, which is `active` immediately for every self-registered account regardless of which capabilities it later gains. `business_staff` (an employee added by a business owner) and `admin` are unrelated to this model — provisioned differently, never self-registered. This superseded an earlier design where `role` was chosen once at registration (`user`/`worker`/`business_owner`) and Worker/Business accounts sat in `pending_verification` from the moment the account itself was created; `WelcomeScreen`'s three role-selection cards were removed accordingly (see above).

**Image uploads (Cloudinary)**: both `workers` and `businesses` modules' `POST .../me/profile` endpoints accept `multipart/form-data`, parsed by a shared `multer` instance (`backend/src/common/middleware/upload.ts` — disk storage to a temp dir, images only, 8MB/file limit) ahead of `validateBody` in the route chain (multer populates `req.body`/`req.files` first, which `zod` then validates — text fields all arrive as strings, so the `workers`/`businesses` validation schemas use `z.coerce` for anything numeric, unlike the JSON-body schemas elsewhere in the app). `backend/src/common/services/cloudinaryService.ts`'s `uploadToCloudinary(filePath, folder)` uploads to Cloudinary and always deletes the local temp file afterward, success or failure — mirrors a pattern already proven in a sibling project, but configured via this app's own `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` env vars (never hardcoded, never shared across projects); if they're unset, `uploadToCloudinary` throws a clear `CLOUDINARY_NOT_CONFIGURED` `AppError` rather than the server failing to boot at all.

**Removed/replaced photos and deleted profiles clean up Cloudinary storage, not just the DB row** — `deletePhotosFromCloudinary(urls)` (same file) is best-effort: a Cloudinary failure is logged and skipped, never thrown, since a storage-cleanup hiccup must never block the user's actual profile update/delete from succeeding. Only the photo URL is persisted (no separate public_id column), so `extractPublicIdFromUrl(url)` parses Cloudinary's own URL structure (`.../upload/v{version}/{public_id}.{ext}`) to find what to delete — both modules' `updateProfile` diff the incoming `existingPhotoUrls` against what's currently stored and delete whatever's no longer kept; `deleteProfile` deletes every photo before removing the row. Any future module storing Cloudinary photo URLs should follow this same "URL is the only source of truth, derive the public_id when cleanup is needed" pattern rather than adding a parallel public_id column.

**Multer's own errors (file too large, wrong type) are mapped to specific responses, not the generic 500** — `multer.MulterError` (thrown internally when a file exceeds `upload.ts`'s size/count limits) and the file-type filter's rejection are neither `instanceof AppError`, so without explicit handling both fell through `errorHandler`'s catch-all into a bare "Something went wrong" 500 with no indication of the actual problem. `errorHandler` (`common/middleware/errorHandler.ts`) now special-cases `err instanceof multer.MulterError` → 400 with a `FILE_UPLOAD_ERROR` code and a limit-specific message (oversized file vs. too many files); the file-type filter (`upload.ts`'s `fileFilter`) calls back with an `AppError.badRequest(..., 'INVALID_FILE_TYPE')` instead of a plain `Error`, so it's caught by the existing `AppError` branch instead of needing its own case. Any future multer-backed upload endpoint inherits this automatically through the shared `errorHandler` — no per-route handling needed.

**Every handled error is logged server-side, not just unexpected ones** — `errorHandler`'s `AppError` and `MulterError` branches both `logger.warn` (code/statusCode/path/details) before responding; previously only the generic-500 fallback logged anything, so a client-reported failure that the backend "handled correctly" (a 400/401/404/409) left zero server-side trace, making it pure guesswork to diagnose after the fact. `upload.ts`'s `logUploadedFiles` middleware (wired into all four Worker/Business multipart routes, right after `multer` parses the request and before validation) logs each received file's name/mimetype/size — so any future upload issue is diagnosable straight from the log instead of reasoned about blind from the client side.

## Auth Flow

1. Full name and mobile number entered (email and location are optional at the API level — `user-app` still collects both; `partner-app` collects neither, see `.cloud/project-context.md`'s Account Model note) → OTP sent.
2. OTP verified → account created (always `role: "user"`, `status: "active"` immediately) → logged in.
3. JWT access + refresh tokens issued.
4. Optionally, at any point: add Worker and/or Business capability (see Account Model above) — each starts `pending_verification` until admin approves, independent of the account itself.

## Authorization

Role-based: `user`, `worker`, `business_owner`, `business_staff`, `admin` (+ future admin sub-roles) — the enum is unchanged, but `worker`/`business_owner` are no longer assigned via self-registration (always `user`, see Account Model above); they remain in the type for any future non-self-registration assignment path. Every protected endpoint checks authentication (valid JWT) and authorization (role/permission) before executing business logic.

## Search Architecture

Area-based for MVP: users select village/town, workers/businesses define service areas — **however, full GPS coordinates are now captured at registration and for Worker/Business capability locations** (see Account Model above), a deliberate, confirmed override of the original "no live GPS in MVP" decision. Search itself is still area/village-town-based for now; the coordinates are captured and stored so radius-based search can build on them later without another migration. Search service is isolated behind an interface so that swap can happen without touching booking/order business logic.

## Verification (PIN) Architecture

```
Booking/Order created → backend generates unique single-use PIN → stored securely
    → customer shares PIN with worker/business staff → PIN submitted → backend verifies
    → status updates only on successful verification
```

Never SMS OTP for this step — in-app only, free, per-booking/per-order.

## Notification Architecture

Firebase Cloud Messaging via a dedicated `notifications` service — never triggered directly from controllers. Other modules call `notifications.service` to enqueue a send.

## Database

PostgreSQL, normalized. Core entities: accounts, otp_verifications, refresh_tokens, worker_profiles, business_profiles, business_staff, bookings, orders, order_items, notifications, reviews, ratings, verification_requests, audit_logs. Foreign keys enforce relationships; index mobile_number, email, skill_category, shop_category, service_area (and other frequently-filtered columns). Full DDL lives in `docs/database.md` / `database/migrations/`.

## Localization Architecture

Language is a core architectural concern, not a display-layer afterthought — see `docs/localization.md` for the full model. The load-bearing points for any module you build:

- `accounts.preferred_language` is the authoritative per-account language; local device storage is a convenience cache synced from it after login.
- APIs are language-independent — never branch business logic on language, never localize API `message`/error text server-side for the client to display. The mobile client maps `error.code` → localized string itself.
- Anything the backend composes and pushes to a user unprompted (notifications, admin announcements) *is* language-aware, but via per-language template lookups keyed by the recipient's `preferred_language` — not translation-on-the-fly.
- Reference/category data (worker professions, business categories) is stored as a stable language-independent code with per-language label lookups, never as translated strings that get re-translated for display.

## Deployment

**Backend (`backend/`) is deployed on Vercel as a serverless function**, not a traditional always-on host — `backend/api/index.js` re-exports `createApp()` (the same factory `server.ts` uses for local dev, just without the `.listen()` call) directly as the function handler, with `backend/vercel.json`'s `rewrites` sending every incoming path to it so the Express app's own `/health`/`/api/v1/...` routing is unaffected. `server.ts` + `npm run dev`/`npm start` are still exactly how local development works; Vercel only ever runs the compiled `dist/app.js` through the thin `api/index.js` wrapper. See `.cloud/project-context.md`'s own deployment note for the full how/why, including the Supabase-pooler-vs-direct-connection gotcha that broke the first deploy (serverless platforms need Supabase's IPv4 connection pooler, not the IPv6-only direct hostname `backend/.env` uses locally) and the exact `vercel` CLI commands used (non-interactive throughout, since this environment has no real TTY).

**`user-app` ships over-the-air JS updates via EAS Update**, not just full APK rebuilds — `app.json`'s `updates`/`runtimeVersion` config plus a `channel` per `eas.json` build profile (`development`/`preview`/`production`) mean `eas update --branch <channel>` pushes a new JS bundle that already-installed builds on that channel pick up without a new APK. `App.tsx` wires `expo-updates`' `useUpdates()` hook to check on launch, on returning to the foreground, and every 5 minutes (skipped entirely in `__DEV__`), download in the background, and show a new `components/UpdateOverlay.tsx` (same full-screen-gradient-overlay convention `LogoutOverlay` already established, extended with a simulated progress bar — `expo-updates`' JS API has no real byte-level download progress, so the bar ramps 5%→88% for the duration of `isDownloading` and snaps to 100% once the update is actually pending) before calling `Updates.reloadAsync()`. Ported from the same pattern already proven in a sibling project (CampuSphere's `app/_layout.jsx`), adapted to this app's own visual language rather than copied wholesale. A full APK rebuild is still needed for anything a JS bundle can't cover (new native permissions/modules, icon/splash changes, `app.json` config changes) — OTA only replaces the JS/asset layer.

## Future Microservices Migration

When a module needs independent scaling (e.g., Notifications or Search under load), extract it because:

- It already exposes a clean service-layer interface.
- It owns its own tables/repository (no cross-module direct queries).
- Its inter-module calls are already abstracted, so they become network calls (REST/queue) instead of in-process calls with minimal contract change.

No module should ever query another module's tables directly — this is the rule that keeps the split cheap later.
