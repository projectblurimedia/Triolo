# Architecture

## Style

Modular Monolith. Three layers:

```
Presentation (mobile app / admin web)
        ↓
Business Logic (Express controllers → services)
        ↓
Data Access (repositories → PostgreSQL)
```

The UI never talks to the database directly; every request goes through backend APIs.

## Backend Module Boundaries

Each feature is an independent module under `backend/src/modules/<name>/`:

```
auth/
users/
workers/
businesses/
staff/
booking/
orders/
notifications/
admin/
ratings/
reviews/
search/
verification/
audit-logs/
```

Each module contains:

```
routes.ts
controller.ts
service.ts
repository.ts
validation.ts
dto.ts
interfaces.ts
tests/
```

Modules communicate only through each other's service interfaces — never by reaching into another module's repository or internal state directly. This is the boundary that makes future microservice extraction possible without a rewrite.

**`admin/` (implemented: list + verify Worker/Business profiles) is the first module that actually needs another module's data** — reviewing `worker_profiles`/`business_profiles.verification_status` is its whole point. It respects the boundary rule above by having no repository of its own at all: `AdminService` depends on `WorkersService`/`BusinessesService`, calling admin-facing methods added to *those* modules (`adminListProfiles`, `adminGetProfile`, `adminSetVerificationStatus`) rather than querying `worker_profiles`/`business_profiles` directly. Those methods' own repository implementations do `JOIN accounts` for review context (`accountFullName`/`accountMobileNumber`/`accountEmail`) — a same-module query against a FK-related table, not a cross-module reach; the boundary rule is about which *module* touches which *table*, and `workers`/`businesses` already own `worker_profiles`/`business_profiles` regardless of who's asking. `admin`'s own routes wire up their own `WorkersService`/`BusinessesService` instances (backed by the same shared `pool`) rather than reaching for a shared singleton — matches how every module's `routes.ts` already instantiates its own repository/service/controller independently; there's no DI container in this codebase. `admin` accounts are provisioned via `backend/scripts/seedAdmin.ts` (`npm run seed:admin -- <mobileNumber> <fullName> [email]`), never self-registered (see Account Model) — the admin then logs in through the **existing** `/auth/login/*` flow, zero new auth code.

## Frontend Structure (user-app/)

Feature-based, mirroring backend modules:

```
src/
  screens/        (auth, home, services, lists, bazaar, user, worker, business, orders, booking, notifications, profile, settings, admin)
  components/     (shared: buttons, cards, inputs, dialogs, loaders, icons, GradientHeader)
  navigation/     RootNavigator (language + theme hydration gate → auth vs. app), AuthNavigator (stack),
                  AppNavigator (bottom tabs)
  services/       (API clients per module)
  hooks/
  state/          Zustand stores, incl. themeStore (theme mode, persisted)
  theme/          colors (brand-constant + light/dark palettes), useThemeColors hook, typography/fonts — Poppins app-wide
  localization/   (en, te)
  utils/
  constants/
  assets/
```

Post-login navigation is a bottom tab bar (`@react-navigation/bottom-tabs`): Home, Services, Prepare List, Bazaar, Profile. ("Bazaar" — the shop-ordering tab was originally named "Shoppify"; renamed to avoid trademark confusion with Shopify and because it reads more naturally in both English and Telugu, "బజార్". "Services" — originally a "Search" tab; the free-text search input lives on Home instead now, and this tab is for browsing by service category. "Prepare List" — added mid-session as an explicit product decision, a 5th tab in the middle of the bar with a `list-check` leading/tab-bar icon (a checklist glyph, switched from an initial `plus` per follow-up feedback — better matches "preparing a list" than "adding" one); `screens/lists/PrepareListScreen.tsx` is a placeholder, same pattern Services/Bazaar started as, with no `ServicesHeader`/`BazaarHeader`-style wrapper since it needs no local UI state yet — it uses the default `screenOptions`-provided `GradientHeader` directly.) Every tab screen is topped by the shared `GradientHeader` component (brand gradient, currently `#0055D3` → `#1D76FA`, constant across themes) — new tabs/screens follow this same header pattern rather than each screen rolling its own. `GradientHeader` supports `showBack` (circular icon-only back button, used on Auth-stack screens instead of the platform-default header), `leadingIcon` (decorative icon beside the title — every tab has one, matching its tab-bar icon: compass for Home's brand header, concierge-bell/list-check/store/user for Services/Prepare List/Bazaar/Profile — its glyph and circular background (`leadingIconButton`, 46px) are both deliberately bigger than the shared `iconButton` (40px) used by the header's back button and right-side actions, since only the leading icon was asked to grow, not every icon in the header), `subtitle` (short tagline under the title — every tab has one, including Home, so no header is just a bare title), and `actions` (right-side buttons — circular icon-only by default, e.g. Home's/Services'/Bazaar's own menu icon; a `HeaderAction` can also carry a `label`, which renders it as a labeled pill instead, for any future header action that needs one — none currently do, since Services/Bazaar's own profile-edit pill was superseded by a body card, see below). Title uses a semi-bold font weight — deliberately between the original bold and an earlier too-light medium pass. Services, Prepare List, and Bazaar are placeholders until the Worker/Business search, list-preparation, and shopping-list modules exist; Home's search bar and filter chips are UI-only for the same reason. Their content should replace the placeholder in place, not add new tabs, unless a product decision changes the tab set (as it did for Prepare List).

**Home, Profile, Services, and Bazaar are exceptions to the shared header**: all four use their own wrapper (`HomeHeader`, `ProfileHeader`, `ServicesHeader`, `BazaarHeader`) instead of the generic per-tab `GradientHeader` config, because their header-triggered UI needs local state (modal/drawer visibility, or a fetched profile driving whether an action icon even shows) that a stateless header render function in `AppNavigator`'s `screenOptions`/`Tab.Screen options` can't hold. `ProfileHeader` wraps `GradientHeader` plus `ProfileMenuModal` (a bottom sheet — language/theme/logout, previously inline in the screen body); its trigger action uses the same `bars` icon every other tab's menu action uses (was `ellipsis-vertical` — the mismatched glyph, not the bottom-sheet-vs-drawer/dock behavior itself, was the "how is it like that" inconsistency per follow-up feedback; the menu's own presentation style still deliberately varies by content shape, see below). `HomeHeader` wraps `GradientHeader` plus `HomeMenuModal` (a right-side drawer — Worker/Business onboarding entry points plus theme/logout, modeled after a reference drawer-menu design: gradient header with an app icon, sectioned list of gradient-icon-square cards with title/subtitle/chevron, an app-settings section, and a footer). `ServicesHeader`/`BazaarHeader` wrap `GradientHeader` plus (respectively) `WorkerProfileModal`/`BusinessProfileModal` in edit mode — see the edit-mode note further below. Any future screen needing header-triggered local UI (a menu, a popover, a conditional action) should follow this same wrapper-component pattern rather than trying to lift state into the navigator config — and pick bottom-sheet vs. side-drawer based on content shape (a handful of settings toggles vs. a scrollable list of navigation entries). **Profile's body is gated on capability existence, not `accounts.role`** (which is always `'user'` for every self-registered account — see Account Model) — sections render per-capability, checking whether `useMyWorkerProfile()`/`useMyBusinessProfile()` resolved a profile, not any role field. For each capability that exists, Profile shows a `ProfileStatsRow` (`components/ProfileStatsRow.tsx` — a small row of icon+value+label tiles, modeled on a reference design the user shared) directly above the *same* `WorkerProfileCard`/`BusinessProfileCard` already used on Services/Bazaar (reused, not duplicated — each card's own `pen` button is the only edit entry point now; an earlier flat "manage profiles" link list was removed as redundant once the cards themselves render here). The stats themselves (Rating, "Services Completed"/"Orders Fulfilled") are placeholder values (`profile.servicesDoneValue`/`ordersDoneValue`, English+Telugu) until the ratings/reviews and booking/order modules exist — same placeholder honesty as the pre-existing rating value, just no longer a dead-end empty-image "Recent Work" grid alongside it.

**Home's menu drawer** (`HomeMenuModal`) surfaces two entry points — "Are You a Worker?" and "Do You Have a Shop?" — opening `WorkerProfileModal`/`BusinessProfileModal` (full-screen forms: skill/shop category chips, experience or shop name, `LocationPicker`, `ImagePickerField`, submit) which add the respective capability to the current `user` account via `POST /workers/me/profile` / `POST /businesses/me/profile` — see the Account Model section below. These two forms use a left-side circular `chevron-left` back button in their header (not a right-side close "X") — they're full-screen forms, not a dismissible overlay, so backing out reads more correctly than closing does; matches `GradientHeader`'s own back button position/style elsewhere in the app. `HomeMenuModal` also carries an "App Settings" section (Language, Theme, Logout) so all three are reachable from Home too, not just Profile's own menu.

**Skill/category chips are multi-select, not single-select** in both `WorkerProfileModal` and `BusinessProfileModal` — a worker can have several skills, a shop can span several categories. Each fixed chip's active state is `array.includes(key)` toggled on press (add/remove from the array), not a single selected-key comparison. `BusinessProfileModal` additionally has a Yes/No delivery-availability chip pair; selecting "Yes" reveals a `deliveryPricePerKm` `TextField` (backend-required in that case). All of these fields are JSON-stringified (arrays) or stringified booleans/numbers client-side before being appended to the `FormData`, since multipart fields are all strings — see `backend/src/common/utils/parseMultipartField.ts`'s `parseJsonIfString`/`parseBooleanIfString` on the receiving end.

**`"other"` is a dedicated "+ Add New" chip, not one of the toggleable category options** — `SKILL_CATEGORIES`/`SHOP_CATEGORIES` no longer include an `"other"` entry at all; instead, an always-visible `+ Add New` chip is appended after the fixed grid (and after any already-committed custom entries), rendered the same way regardless of state, so it's always available to add another. It's a filled tinted pill, not a dashed outline — `borderColor: accentColor` + `backgroundColor: ${accentColor}16` (a light alpha tint, matching `LocationPicker`'s detect-button tint convention) plus a small solid-fill circular badge (`addNewBadge`, 16px, accent-colored background with a white `plus` glyph) instead of a bare icon, reading as a deliberately-designed action chip rather than a placeholder/disabled-looking dashed box. Tapping it opens an inline `TextField` + circular gradient "Done" button (`otherInputValue`/`showOtherInput` state). Confirming (the Done button or the keyboard's own `returnKeyType="done"`) resolves the typed text in this order: (1) if it case-insensitively matches one of the fixed grid's translated labels (e.g. typing "Grocery"), that fixed chip is selected instead of creating a redundant custom tag; (2) else if it case-insensitively matches an already-committed custom entry, that existing entry moves to the front of the array (visible feedback that "you already added this" rather than a silent no-op or a duplicate); (3) else it's appended as a new entry. Either way the input clears and closes — tapping `+ Add New` again reopens it for another entry. Each committed custom entry renders as its own small removable gradient chip (tapping one removes it by index, since it isn't a fixed key with array-membership toggling). At submit time, if any custom entries exist, `"other"` is appended to the fixed-category array being sent and all entries are joined with `", "` into the single `otherSkillDescription`/`otherCategoryDescription` string the backend's `.refine()` validation expects (the backend has no concept of *multiple* other-entries — the join happens client-side).

**The fixed category grid re-sorts selected-first on every render** — `orderedSkills`/`orderedCategories` is a fresh `[...BASE_LIST].sort((a, b) => Number(selected.includes(b.key)) - Number(selected.includes(a.key)))` computed each render (JS's `Array.sort` is stable, so ties keep their original relative order), not a `useMemo` — the list is short (7-8 items) so re-sorting on every keystroke elsewhere in the form is cheap, and memoizing would need `selected` in the dep array anyway, i.e. no real saving.

**`WorkerProfileModal`/`BusinessProfileModal` double as edit forms**: an optional `profile` prop (the existing `WorkerProfile`/`BusinessProfile`, or `undefined`/`null`) switches the whole modal between create and edit mode (`isEditMode = !!profile`) — same form, same validation, same chip/tag UI, just prefilled via a `useEffect` keyed on `[visible, profile]` (skill/category arrays split into fixed-grid keys vs. `otherSkillDescription`/`otherCategoryDescription`.split(', ') for the custom tag chips, existing photo URLs turned into `PickedImage`-shaped entries so `ImagePickerField` can show and let the user remove them like any other picked image). Submit branches to `useUpdateWorkerProfile()`/`useUpdateBusinessProfile()` instead of the create mutations; photos are split back apart at submit time by `uri.startsWith('http')` — remote ones go to `existingPhotoUrls` (kept, not re-uploaded), local ones go through the same multipart file upload as create. Edit mode also shows a red "Delete Profile" text action at the bottom, gated behind a new generic `ConfirmModal` (`components/ConfirmModal.tsx` — parameterized icon/gradient/title/message/confirmLabel, factored out of what was previously `LogoutConfirmModal`-only so other destructive confirmations don't need their own one-off modal) calling `useDeleteWorkerProfile()`/`useDeleteBusinessProfile()`.

**Three entry points open the same edit-mode modal**: Home's menu still creates (`profile` omitted); `ServicesScreen`/`BazaarScreen`'s own `WorkerProfileCard`/`BusinessProfileCard` (rendered at the top of the screen body once `useMyWorkerProfile()`/`useMyBusinessProfile()` resolves a non-null profile — see below) carry the edit action; and Profile screen's own "Manage Your Profiles" section (tappable rows, shown only for whichever capabilities exist) opens the same modals directly from the screen body. All three just pass the already-fetched profile into the same `WorkerProfileModal`/`BusinessProfileModal` — there's no separate "edit screen." (`ServicesHeader`/`BazaarHeader` themselves no longer carry any profile-dependent UI — see the header-menu note further below for why that moved out of the header entirely.)

**Worker/Business profile summary cards, not a header pill, once the profile exists** — `WorkerProfileCard`/`BusinessProfileCard` (`components/`) render at the top of `ServicesScreen`/`BazaarScreen`'s body: fixed skill/category chips plus any custom "other" entries (split from `otherSkillDescription`/`otherCategoryDescription` the same way the edit-mode prefill does), a shared `VerificationBadge` (`components/VerificationBadge.tsx` — maps `verification_status` to a color/icon/label, reused by both cards so the mapping isn't duplicated), experience-years or delivery-availability, and location — plus a `pen` edit button opening the same `WorkerProfileModal`/`BusinessProfileModal` in edit mode. This replaced an earlier header-pill approach (a `HeaderAction` with a `label`, shown in `ServicesHeader`/`BazaarHeader` only once the profile query resolved) — the pill popping into the header chrome after the tab was already visible read as a UI glitch; a card appearing in the body as data loads in is a much more expected pattern. `BusinessProfileCard` imports `SHOP_GRADIENT` from `BusinessProfileModal` (exported from there) rather than redefining the orange gradient.

**Services/Bazaar's header menu icon opens a compact floating icon dock, anchored just below its own header** — with the edit pill gone, `ServicesHeader`/`BazaarHeader`'s right-side action is a plain `bars` icon (matching Home's own header exactly) opening `SideDockMenu` (`components/SideDockMenu.tsx`): a rounded panel (72px wide — wide enough for a short text label under each icon, not just an icon-only pill), positioned `insets.top + HEADER_CONTENT_HEIGHT + DOCK_GAP` from the top — `DOCK_GAP` (16) is the *same* constant used for the dock's own right-edge gap, so the gap below the header visually matches the gap from the screen edge instead of two independently-chosen numbers (an earlier pass centered the dock vertically on the whole screen instead, which didn't read as connected to the menu button that opened it). Background is a `LinearGradient` using the exact same two-stop gradient as its own header (`gradient` prop — `headerGradient` for Services, `SHOP_GRADIENT` for Bazaar — not a flat fill), stacked icon+label buttons with thin dividers, fading + sliding down into place (fixed-duration `timing`, not `spring`, per the drawer-animation rationale elsewhere in this doc — sliding down makes sense again now that the dock is tethered to the header it opens from). `SideDockMenu` is otherwise generic (`items: SideDockItem[]`, `onSelectItem` callback); `ServicesHeader`/`BazaarHeader` currently pass static placeholder items (Filters/Sort/Favorites/History or Orders) with no real behavior wired up yet — `onSelectItem` just closes the menu and shows a "coming soon" toast. This replaced an earlier `GridMenuModal` (a spin-and-scale 2-column tile grid) built the same session — deleted rather than kept as a dead alternative once `SideDockMenu` took over both call sites; any future functional menu item should replace the placeholder `onSelectItem` branch for that specific item, not restructure the component.

**Bazaar's tab chrome (header + `SideDockMenu`) now uses the constant brand blue, matching every other tab — orange stays only on `BusinessProfileCard`/`BusinessProfileModal`.** `GradientHeader` takes an optional `gradient` prop (defaulting to the constant brand-blue `headerGradient`) — `BazaarHeader` originally passed `SHOP_GRADIENT` (imported from `BusinessProfileModal`) here and to `SideDockMenu`, so Bazaar's top chrome matched the orange identity established for Business elsewhere (the profile modal, the profile card, the icon dock). Per two rounds of follow-up feedback — first scoping the fix to just `CustomTabBar`'s `ACTIVE_GRADIENTS.Bazaar`, then clarifying "the header and its menu too" — `BazaarHeader` no longer passes a `gradient` override to `GradientHeader` at all (falls through to the default `headerGradient`) and passes `headerGradient` explicitly to `SideDockMenu`. `SHOP_GRADIENT` is no longer imported into `BazaarHeader` at all; it remains exported from `BusinessProfileModal` and used by `BusinessProfileCard`/`BusinessProfileModal` themselves, which represent the *Business capability* identity (reachable from Home's menu and Profile too, not just the Bazaar tab) rather than "the Bazaar tab's own chrome" — that distinction is what's now actually reflected: capability-identity color stays orange everywhere it appears; tab-chrome color (header, menu, tab bar) is uniformly blue across all tabs including Bazaar.

**The bottom tab bar is a floating pill card whose active-tab dot lives inside the bar, just below its icon — not floating above the bar the way an earlier version of this component had it, not `@react-navigation/bottom-tabs`' default rendering either** — `CustomTabBar` (`components/CustomTabBar.tsx`) is passed via `Tab.Navigator`'s `tabBar` prop (`AppNavigator.tsx`). This is a full replacement of every earlier design of this component (a concave SVG notch with an overlapping bubble, an iOS-glass blurred pill with a sliding icon+label capsule, a version of this same pill design with the dot floating above the bar instead of inside it) — none of those are iterated on or reused. `position: 'absolute'` on the outer wrapper keeps it contributing ~0 height to `BottomTabView`'s flex layout, so screens render full-height and scroll behind the floating bar, same rationale as every earlier version. The bar itself (`styles.bar`) is a `colors.surface` pill (`BAR_RADIUS = BAR_HEIGHT / 2`, `BAR_HEIGHT = 66` — taller than earlier versions specifically to give the icon+dot stack room) with margin on every side and a plain platform shadow (`elevation` on Android, `shadowOffset`/`shadowOpacity` on iOS) — no blur, deliberately: `expo-blur`'s Android blur method needed several fix passes in an earlier iteration and was dropped entirely along with the glass design it supported. `paddingHorizontal: BAR_PADDING_H` (5) on the bar itself keeps the first/last tab's content a small, deliberate distance in from the bar's own rounded edge. This design is icon-only — no tab labels — matching every prior version's decision. It floats by the same amount on every side: `MARGIN_H` insets the bar from the left/right screen edges, and `barBottom = Math.max(insets.bottom, MARGIN_H)` keeps the bottom gap at least `MARGIN_H` too (growing beyond it only if the device's own safe-area inset genuinely needs more clearance than that) — `wrapper`'s `justifyContent: 'flex-end'` is what makes this margin actually reach the screen; several earlier rounds of "still too much gap" reports turned out to be about `wrapper` never bottom-aligning its (taller, at the time, to reserve room for the since-removed above-bar dot) content at all, not about `barBottom`'s value.

**Each tab stacks its own dot directly below its own icon, inside `tabContent` (a plain centered column), rather than one dot sliding between tabs** — moving the dot inside the bar removed the need for it to travel horizontally to whichever tab is active (an earlier version's `dotX`/`Animated.spring`/`translateX` slide, plus a `dotOuter` positioned above the bar with an Android-only `glowRing` to fake a colored glow that plain `elevation` can't produce) entirely: with one dot living permanently under each tab's own icon, all that's left is fading it in/out with that tab's own `progress` value, the same one already driving the icon crossfade. `dotShadowWrap` (`DOT_SIZE = 6`) wraps a `LinearGradient`-filled circle in that tab's own gradient color, with a real tinted iOS shadow (`shadowColor` set inline) and a plain `elevation` on Android (no glow-ring fake needed now — the dot's small, contained size next to its icon doesn't call for the same emphasis the old floating dot did).

**Every tab's icon sits at the bar's true vertical center at rest; only the selected tab's icon lifts up on selection, revealing its dot below it — the dot is never allowed to permanently reserve layout space that would push icons off-center.** An initial version of this "dot below the icon" layout gave `dotShadowWrap` a `marginTop` inside the same normal-flow column as `iconArea` — since the dot is always present in the tree (only its `opacity` animates, so unselected tabs render it invisibly, not unmounted), that `marginTop` was *always* reserved, on every tab, shifting every icon up from the bar's true center uniformly — which is what actually broke "all icons vertically centered," not any per-tab inconsistency. The fix: `dotShadowWrap` is `position: 'absolute'` (`top: ICON_BG_SIZE + DOT_MARGIN_TOP`, `DOT_MARGIN_TOP` trimmed 4 → 2 → 1 → 0.5 → 0 across follow-up feedback to tighten the icon-to-dot gap, then to `-2` per a final request to move the dot up slightly past flush (a small deliberate overlap into the icon's own backdrop box, not visually into the icon glyph itself), anchored against `tabContent`'s own box) rather than a flow-affecting margin, so `tabContent`'s size — and therefore `iconArea`'s centered position within `tabButton` — is driven by `iconArea` alone. `iconArea` itself is now the `Animated.View` carrying a `translateY` (`iconLift`, `progress`-driven, `0 → -6`) — since `transform` is a paint-time effect that never affects an element's own layout box, animating it doesn't disturb the centering math above: at rest (`progress = 0`) the icon sits exactly where `tabContent`'s centering places it (the bar's true vertical center), and only on selection does it visibly rise, opening up the gap to its dot below (which stays anchored to the icon's *resting*, not lifted, position, so the gap is what visibly grows).

**Per-tab icons cross-fade between muted and brand-colored, plus a soft tinted circle that visibly pops larger behind the active one, all driven by `Animated.Value`s on the native (UI) thread** — `progressAnims[index]` runs `0 → 1` via `Animated.timing` (260ms, `easing: Easing.out(Easing.cubic)`, `useNativeDriver: true`) whenever that tab becomes/stops being active; an earlier pass left this on the JS driver (`useNativeDriver: false`, out of an abundance of caution around color interpolation that these values don't actually do), which is what read as not-quite-smooth — every value this drives is opacity/transform only, so native-driving it was safe and is what actually fixed the jank. Rather than animating a vector-icon component's `color` prop directly (unreliable — `FontAwesome6` is a composite component wrapping an internal glyph, not a plain host view, so there's no guarantee `Animated.createAnimatedComponent` can push prop updates through it), each tab renders **two** plain, statically-colored icons stacked in the same box and cross-fades their wrapping `Animated.View`s' `opacity` — a muted-color one fading out (`Animated.subtract(1, progress)`) and a gradient-colored one fading in (`progress` directly), the same "stack two versions, cross-fade via opacity on a wrapping Animated.View" technique earlier versions of this component used for SVG notch paths. `iconBg` (`ICON_BG_SIZE = 40` — brought back down from an earlier 52 now that it has to share the bar's vertical space with the dot below it rather than owning the bar's full height alone — a circle tinted `${gradient[0]}1A`, a light alpha wash matching `LocationPicker`'s own detect-button tint convention, sized and positioned to exactly fill `iconArea`) fades/scales in behind the icon on the same `progress` value. The earlier `lift` (`translateY`, reaching the icon/backdrop up toward a dot that floated above them) is gone entirely along with that dot — with the dot now below the icon instead, there's nothing above to reach toward, so both views now animate scale only. A separate, shared `popScale` value (reset to `0.7`, sprung back to `1` with `friction: 5`/`tension: 180` — underdamped enough to overshoot slightly past `1` before settling) is stacked as an *additional* `scale` transform on `iconBg` and the dot, so the selected tab's backdrop and dot both visibly grow a little larger than their resting size on selection instead of just linearly scaling up — applied unconditionally to every tab (harmless on the others, since their opacity is fading toward `0` regardless). Deliberately not applied to the icon glyph itself (`iconScale`, capped at a modest `1.08`) — an earlier version stacked `popScale` onto the icon too, and the icon's overshoot could momentarily outgrow its own backdrop circle during the spring, reading as the icon poking out past its background. Keeping the pop off the icon guarantees it stays visually contained at every point in the animation, not just at rest.

**Per-tab colors are a `LinearGradient` tuple, not a flat color** — `ACTIVE_GRADIENTS` maps each route name to a two-stop gradient; Bazaar resolves to its own `SHOP_GRADIENT` (matching its header, `SideDockMenu`, and `BusinessProfileCard`), every other tab resolves to the constant brand-blue `headerGradient` — same mapping (renamed from the earlier bubble/capsule designs' own gradient maps) every prior version of this component has used.

**Toasts, not `Alert.alert`, for every app-surfaced message** — `Alert.alert` is a native OS dialog: blocking, modal, and visually inconsistent with the rest of this app's design language. Replaced everywhere (profile-creation success, permission-denied, GPS-detect-failure, post-registration pointer) with `showToast({ variant, title, message })` (`state/toastStore.ts`, a plain zustand store holding at most one active `ToastMessage` — a new one replaces whatever's showing, matching `Alert`'s own one-at-a-time behavior, no queue needed for this app's usage). `components/ToastHost.tsx` is mounted once at the root in `App.tsx` (a sibling of `RootNavigator`, same pattern as `LogoutOverlay`) and renders whatever `toastStore.toast` currently holds: a floating card below the safe-area top inset, gradient icon circle keyed by `variant` (`success`/`error`/`info` — success green, the same red as `LogoutConfirmModal`, and brand blue respectively) plus a matching left accent bar, sliding down/fading in via `Animated.timing` (not `spring` — same rationale as the drawer animation elsewhere in this doc) and auto-dismissing after ~3.2s, or immediately on tap. `showToast()` is a plain exported function (not a hook) specifically so it can be called from `onSuccess`/`onError` mutation callbacks and other non-component code, the same call sites `Alert.alert` used to occupy.

**Language, Theme, and Logout share dedicated modals across both menus**: `LanguagePickerModal` and `ThemePickerModal` (centered cards — gradient header, selectable option rows with a per-option gradient icon and a checkmark on the active one; `LanguagePickerModal` mirrors `ThemePickerModal`'s structure exactly) replace inline switcher pill rows in both `HomeMenuModal` and `ProfileMenuModal` — each now shows Language/Theme as a tappable row (icon, label, current value, chevron) instead. `LogoutConfirmModal` (centered card, red gradient icon circle, title/message, Cancel + red-gradient Logout buttons) gates the actual `useLogout()` call behind an explicit confirmation in both menus; the Logout trigger itself is a distinct red gradient (`#ef4444` → `#dc2626`) — a deliberate, intentional exception to the "every primary button uses the brand gradient" rule below, reserved for this one destructive action. `state/themeStore.ts` exports `themeModeLabelKey(mode)` and `state/settingsStore.ts` exports `languageLabelKey(language)` so both menus resolve the same "current value" label without duplicating the mapping.

**`ProfileMenuModal`, `ThemePickerModal`, and `LogoutConfirmModal` use the platform `Modal`'s built-in `animationType="fade"` plus `statusBarTranslucent`** — no custom `Animated`-driven transition, since none of them need a directional effect the built-in type can't express. **`HomeMenuModal` is the one exception**: it's a genuine slide-in drawer (per its reference design), which `animationType` has no built-in equivalent for, so it drives its own `Animated.timing` on `translateX`/backdrop opacity — but deliberately `timing`, not `spring`, for both open *and* close. The very first version of this drawer used a `spring` for its close animation; a spring has no fixed duration (it runs until it settles within a threshold, which can take an unpredictable extra beat), and since the native `Modal` stays mounted — and keeps swallowing all touches, including the header's own menu button — until that animation reports `finished`, an unpredictable spring-close made reopening the drawer right after closing intermittently feel broken. A fixed-duration `timing` (with `Easing.out(Easing.cubic)` for the deceleration feel) keeps the slide smooth while guaranteeing the Modal frees up input again after the same short, known window every time. Any new modal in this app should default to the platform's own `animationType`/`statusBarTranslucent`; reach for a custom `Animated` transition only when there's a concrete directional-motion requirement the built-in types can't express, and prefer `timing` over `spring` for anything that also needs to unblock touches promptly on close.

**Loading affordances all use one shared motif — dots orbiting a center point (`LoadingIndicator`)** — instead of the platform's generic `ActivityIndicator`. `LoadingIndicator` (`size`/`color`/`dotSize`/`duration` props) is what `Button`'s `loading` state renders, so every submit button in the app (Register/Login/Otp, etc.) picks it up automatically. **Logout gets a dedicated full-screen variant**: `authStore.isLoggingOut` (set in `useLogout()`'s `onMutate`, cleared in `onSettled` — after `clearSession()`, so `RootNavigator` has already swapped to the Auth stack by the time the overlay starts fading) drives `LogoutOverlay`, rendered from `App.tsx` as a sibling of `RootNavigator` so it draws above whichever navigator is mounted regardless of the swap happening underneath it. `isLoggingOut` is deliberately excluded from `authStore`'s persistence (`partialize`) — a stuck `true` surviving an app kill mid-request would otherwise show the overlay forever on next launch. `LogoutOverlay` composes a large `LoadingIndicator` (`size={96}`, `duration={1800}` — slower than the default 900ms, since a bigger ring spinning at the same speed reads as frantic) plus a pulsing center mark unique to this full-screen variant — logging out is the one transition where the whole screen is about to change underneath the user, so it earns its own full-screen beat rather than just a bigger version of the inline spinner alone.

**`WelcomeScreen`** (the Auth stack's entry point, and where logout always lands) is a full landing screen, not a bare button stack: a gradient hero panel (`headerGradient`, the same treatment `GradientHeader` uses — brand icon, app name, tagline) followed by a single "Create Account" `Button` and a plain text "Already have an account? Log In" link. It's deliberately **not** a role picker — every self-registered account is a plain `user` (see Account Model below), so there's no role choice to make here; an earlier version had three role-selection cards (Customer/Worker/Business) before that model was settled. It intentionally does **not** use the shared `ScreenContainer` (which applies a fixed `padding: 20` on all sides) — the hero panel needs to bleed edge-to-edge and up under the status bar the way `GradientHeader` does, so the screen composes its own `SafeAreaView`s directly instead.

**Icons**: `FontAwesome6` (`@expo/vector-icons`), not Ionicons — the free tier's icon set is mostly solid-only (no outline counterpart for `home`/`magnifying-glass`/`store`/`bars`/`arrow-left`/`screwdriver-wrench`). Solid vs. regular style is selected via a boolean prop (`solid`) matching the style name, same mechanism FA5 used — not an `iconStyle` string prop, despite an internal `FA6Style` const suggesting otherwise. Migrated from FA5 solely to get the `screwdriver-wrench` glyph (Services tab); FA6 also renamed a couple of glyphs used elsewhere in the app (`search` → `magnifying-glass`, `times` → `xmark`). `CustomTabBar`'s own icon/backdrop/glow-dot treatment (see above) is this app's one deliberate exception to "no background pill or per-icon glow" — it's the primary way active-tab state reads, not decoration; any *other* new tab or header icon should stay plain color-only unless it specifically needs its own active-state indicator. Follow the same icon family for any new tab/header icon regardless.

**Buttons**: the shared `Button` component and the active pill in `LanguageSwitcher`/`ThemePickerModal` all render the brand gradient as their background (via `LinearGradient`, since a `Pressable`/View can't have a gradient `backgroundColor` directly) — never a flat `colors.primary` fill. Any new primary-action control should follow this pattern for visual consistency. The one deliberate exception is Logout (`HomeMenuModal`/`ProfileMenuModal`'s trigger and `LogoutConfirmModal`'s confirm button), which uses a distinct red gradient (`#ef4444` → `#dc2626`) instead — a destructive/exit action, not a primary one, so it's intentionally visually distinct rather than blending in with every other button in the app. `Button` takes an optional `gradient` prop (defaulting to `headerGradient`) precisely so a screen with its own brand-distinct gradient header can keep its submit button visually consistent with that header instead of the app-wide blue — `BusinessProfileModal` passes its orange `SHOP_GRADIENT` (`#F59E0B` → `#D97706`, matching its own header) rather than introducing a separate flat-orange button style.

**Light/dark theme**: only `background`/`surface`/`text`/`textMuted`/`border` vary between `lightColors` and `darkColors` (`theme/colors.ts`, currently `#F9FCFF`/`#0c0f14` background/text swapped between the two) — brand colors (primary, secondary, success/warning/error, the header gradient) stay constant in both. Any component that renders one of the theme-dependent keys must read it from `useThemeColors()` inside the component body (so it re-renders on theme change), never from the static `colors` export — `StyleSheet.create()` at module scope can't be reactive, so theme-dependent values are applied via inline `style={[...]}` overrides, not baked into the stylesheet. `themeStore` only persists the user's choice (`system`/`light`/`dark`); `useThemeColors()` resolves `system` against the device's live scheme on every render.

`RootNavigator.tsx` also passes a `theme` to `<NavigationContainer>` built from `useThemeColors()` (based on React Navigation's own `DefaultTheme`/`DarkTheme`) — without this, React Navigation's hardcoded default (light) background shows through anywhere screen content doesn't fully cover it. Any future navigator added at the root level inherits this automatically; don't reintroduce a bare `<NavigationContainer>` without the `theme` prop.

**Status bar**: `App.tsx`'s `<StatusBar style="light" />` is hardcoded, not theme-reactive — every screen's persistent top chrome is the blue gradient header, so the status bar overlaying it needs light text/icons in both light and dark mode. Don't switch this back to `"auto"` without also removing/reworking the gradient header, since `"auto"` would make status bar text unreadable against the gradient whenever the in-app theme is light.

**Native chrome outside the React tree**: Android's edge-to-edge system navigation bar (and the native root window background it reveals) isn't part of the component tree at all — no amount of in-app `View`/`StyleSheet` styling reaches it. `App.tsx` syncs it explicitly on every theme change: `expo-system-ui`'s `SystemUI.setBackgroundColorAsync(colors.surface)` (root window background — this is what a mismatched `NavigationContainer` theme was actually leaking through, not an Android rendering bug in the tab bar itself) and `expo-navigation-bar`'s `NavigationBar.setStyle(...)` (Android-only, nav bar icon color). Synced to `colors.surface`, not `colors.background` — the system back/home/recents bar sits directly below `CustomTabBar`, which is itself `colors.surface`, so using `colors.background` there left a visible seam where the two met; `expo-navigation-bar` 57.0.1 has no `setBackgroundColorAsync` of its own (Android enforces edge-to-edge now, so the nav bar itself is always transparent) — `SystemUI`'s root-window-background call is the only mechanism that reaches this area. Also: `app.json`'s `userInterfaceStyle` must stay `"automatic"`, not `"light"` — that setting locks the *native* Android appearance independent of `themeStore`'s in-app choice, which directly undermines the dark mode feature if ever changed back.

**`LocationPicker`** (`user-app/src/components/LocationPicker.tsx`) is "Use my current location" (`expo-location`'s `requestForegroundPermissionsAsync` → `getCurrentPositionAsync` → `reverseGeocodeAsync`, building a display address from `name`/`city`/`region`) with a manual `TextField` fallback. There's no map/pin-drop UI yet, so manual entry only ever produces an address string — `latitude`/`longitude` stay `null` until GPS actually succeeds; editing the address text after a successful GPS detect clears the coordinates too, since the text no longer necessarily matches them. Used by `RegisterScreen` and both `WorkerProfileModal`/`BusinessProfileModal`. Takes an optional `accentColor` prop (defaulting to `colors.primary`) for its "use current location" button's border/tint/icon color — `BusinessProfileModal` passes `SHOP_GRADIENT[0]` so this button matches its orange header instead of defaulting to brand blue, the same rationale as `Button`'s `gradient` prop above.

**`ImagePickerField`** (`user-app/src/components/ImagePickerField.tsx`) follows the pick-then-upload-on-submit flow proven in a sibling project: `expo-image-picker`'s `requestMediaLibraryPermissionsAsync` → `launchImageLibraryAsync` (gallery only, no camera) holds picked images as local URIs in component state for preview; the actual multipart upload only happens when the surrounding form is submitted (`workersService`/`businessesService` build a `FormData` with `{uri, name, type}` file objects — the shape React Native's networking layer expects for a file entry, not a real `Blob`). `apiClient.postForm()`/`patchForm()` are the two places that send a `FormData` body instead of JSON — `Content-Type` is explicitly `multipart/form-data` with no boundary; React Native's networking layer fills the boundary in itself when it sees that exact header paired with a FormData body.

**`apiClient.ts` is built on `axios`, not React Native's built-in `fetch`** — matches the networking approach already proven reliable in a sibling project (CampuSphere's `CreateStudent` photo upload), adopted after `fetch`-based multipart uploads proved unreliable for Worker/Business photos in this Expo/RN version despite several targeted fixes (token-refresh retry, multer error handling, MIME-type inference) not resolving it. In React Native, `axios` resolves to the `XMLHttpRequest`-based adapter — a genuinely separate native networking code path from `fetch`, which has its own history of RN-version-specific quirks around multipart bodies. The `axios.create()` instance (`baseURL`, 45s `timeout`) is module-scoped in `apiClient.ts`; every method (`get`/`post`/`patch`/`delete`/`postForm`/`patchForm`) routes through it, so the public interface every service file (`authService`/`workersService`/`businessesService`) calls never changed. Any future networking change should stay on this same axios instance rather than reintroducing `fetch` anywhere in the app.

**Token refresh is single-flight, not per-request** — `apiClient.ts`'s `tryRefreshAccessToken()` shares one module-level `refreshPromise` across every concurrent caller instead of each 401'd request independently hitting `/auth/refresh`. This matters because refresh tokens rotate on use (single-use — the backend revokes the old one and issues a new pair on every refresh call, by design, for security): screens like Profile/Services/Bazaar all fire several authenticated queries in parallel on mount (worker profile, business profile, account info), so if the access token has expired, multiple requests can hit 401 within the same instant. Without dedup, each would call `/auth/refresh` with the same still-valid-looking refresh token — only the first to reach the server wins (its call rotates the token), and every other concurrent refresh attempt gets its own 401 (using an already-revoked token), which used to `clearSession()` and silently log the user out mid-flow. Any future authenticated-request helper (a new `apiClient` method, a websocket reconnect, etc.) must route through this same shared `tryRefreshAccessToken()` rather than rolling its own refresh call, or the race reopens.

**Token refresh also happens proactively, not just reactively on a 401** — `ensureFreshAccessToken()` decodes the access token's own `exp` claim (a small dependency-free base64url decoder, `base64UrlDecode()`, since RN/Hermes doesn't reliably provide global `atob`) and refreshes ahead of time if it's within 20s of expiring, called at the top of both `request()` and `requestForm()` before the request is built. This matters specifically for multipart uploads: re-sending the *same* `FormData` instance a second time (the previous reactive-only retry-on-401 behavior) is not something React Native's networking layer reliably supports once a file part has already been handed off once — a request that goes out with an already-stale token could fail on its retry too, with a *different*, non-401 error that wasn't retried again, surfacing as an opaque failure on the first submit attempt while a manual second attempt (a fresh `FormData`, and a by-then-refreshed token) just worked. Proactive refresh means the common case (token simply expired mid-form-fill) never reaches the reactive-retry path at all — the FormData is only ever sent once, already carrying a fresh token.

## Frontend Structure (partner-app/)

A second, standalone React Native (Expo) app — **Triolo Partner** — for Worker/Business registration and login, added as an explicit product decision (see "Cold-start supply" below) rather than folded into `user-app` as another optional flow. Same backend, same account model as `user-app`'s (a phone number registered here is the *same account*, just reached capability-first) — but a genuinely separate Expo project, not a monorepo package: this repo has no root `package.json`/workspace tooling (`user-app`/`backend` are plain sibling folders), so `partner-app` follows that same pattern rather than introducing workspace infrastructure just for this. That means no direct code import between the two apps — `partner-app` re-implements (copies, then adapts only what's genuinely Partner-specific) `user-app`'s already-proven `theme/`, `apiClient.ts`, `authStore`/`themeStore`/`settingsStore`/`toastStore`, `LocationPicker`/`ImagePickerField`/`GradientHeader`/`ConfirmModal`/`VerificationBadge`/`ToastHost`/`LogoutOverlay`, and the auth OTP screens verbatim, rather than sharing a package. **A fix or improvement to any of those in one app should be checked against the other** — there's no tooling that keeps them in sync automatically.

**Deliberately minimal for this first pass**: no first-launch language picker, no inline language switcher (`user-app` has both) — device locale still drives en/te via `i18n.ts`, and an account's saved `preferredLanguage` still overrides it on login (same `authStore.setSession` behavior). No bottom tab bar — `MainNavigator` is a plain stack (`ChooseCapability` → `WorkerRegistration`/`BusinessRegistration` → `MyInfo`), since this app's whole surface *is* registration + one status screen, not a multi-section product to tab between. `MyInfoScreen` is **read-only** — no edit/delete yet, even though the backend `PATCH`/`DELETE .../me/profile` endpoints it would need already exist and are proven by `user-app`'s own `WorkerProfileModal`/`BusinessProfileModal`; wiring them here is a natural, low-risk follow-up, just not built until asked for.

**`ChooseCapabilityScreen`** is the app's home base (lands here after login/registration): fetches `GET /workers/me/profile` and `GET /businesses/me/profile` and renders one card per capability, styled after `user-app`'s `HomeMenuModal` entry-card pattern (gradient icon square, title/subtitle, chevron) — a capability that doesn't exist yet opens its registration screen on tap; one that does opens the read-only `MyInfoScreen` instead, showing its `VerificationBadge`. `WorkerRegistrationScreen`/`BusinessRegistrationScreen` are `user-app`'s `WorkerProfileModal`/`BusinessProfileModal` adapted from a `Modal` overlay into a plain navigator screen (create-only — the edit-mode branch, delete action, and their `ConfirmModal` wiring were dropped, not adapted) — same fields, same multi-select category chips + "+ Add New" pattern, same shared `LocationPicker`/`ImagePickerField`, same `POST .../me/profile` endpoints.

**Cold-start supply**: this app exists to solve the two-sided-marketplace bootstrap problem — requiring a Worker/shop-owner to install and navigate the full consumer app just to register was too much friction. The other half of that problem — reviewing/verifying what comes in, and reaching someone who won't install *any* app — is `registration-web/` + `admin-web/` (see below), built as a follow-up once the backend `admin` module existed to support it.

## Frontend Structure (registration-web/, admin-web/)

This project's first web frontends — Vite + React + TypeScript, plain CSS. **Two separate sites, not one** — an initial combined `web/` app (Admin dashboard + public registration forms together) was split into `registration-web/` (only ever `/`, `/worker`, `/business` — no admin anything, not even a link to it) and `admin-web/` (`/login`, `/`, `/workers/:id`, `/businesses/:id`) per explicit follow-up feedback, so the two audiences ship as genuinely independent deployments rather than routes on the same domain. **Why Vite, not Next.js**: neither site needs SSR/SEO — an internal tool and a handful of short-lived public forms — so the lower-setup-cost choice matches `docs/vision.md`'s "simple, lightweight, low-cost" MVP principle. No shared package between them, or with `user-app`/`partner-app` (same reasoning as `partner-app`'s own — no workspace tooling in this repo): `apiClient.ts`, `authStore.ts`, `errorMessages.ts`, `theme/tokens.ts`/`global.css` (the same `#0055D3`→`#1D76FA` gradient, Poppins via Google Fonts) are duplicated across both sites and kept in sync manually — flagged in both READMEs.

**`apiClient.ts` is simpler than the mobile apps', not a copy** — a browser's `fetch`+`FormData` is safe to resend on retry (unlike React Native's, which is why the mobile apps' client proactively decodes the JWT and refreshes ahead of every request), so this one just does a plain reactive refresh-once-on-401. Session lives in `authStore`, a `localStorage`-persisted Zustand store (Zustand works identically outside React Native) — harmless for the public registration flow too, since it lets someone reopen their own registration link later and see their status.

**`PageHeader` is deliberately shorter than the mobile apps' `GradientHeader`, and website-only** — reduced vertical padding, no subtitle line at all (the mobile apps' header design is unchanged; this is a website-specific simplification, not a cross-platform one), and a back button (when given a `backTo` path) rendered *beside* the title in the same row, not stacked above it. The back icon is FontAwesome's `chevron-left` via `@fortawesome/react-fontawesome` + `@fortawesome/free-solid-svg-icons` (both sites' first real icon-library dependency — the earlier combined `web/` app had none, using plain text/emoji glyphs instead). `PageHeader` is duplicated between the two sites like the rest of the shared infra above.

**`registration-web`'s `PhoneAuthFlow`** (shared by `RegisterWorkerPage`/`RegisterBusinessPage`, *not* `admin-web`'s `AdminLoginPage`) tries `/auth/login/request-otp` first; an `ACCOUNT_NOT_FOUND` response falls through to a short name/email step before requesting a registration OTP instead — one flow covers "I already have a Triolo account" and "I'm brand new" without asking the person to choose up front. The two registration pages mirror `partner-app`'s `WorkerRegistrationScreen`/`BusinessRegistrationScreen` field-for-field (same category-chip + "+ Add New" pattern via `CategoryChips`) but with browser-native inputs: `PhotoUpload` (`<input type="file" multiple>`) instead of `expo-image-picker`, `LocationField` (the browser Geolocation API) instead of `expo-location` — no reverse-geocoding here, since the mobile apps' comes from `expo-location`'s device-native geocoder with no direct browser equivalent short of a paid API, so a GPS-detected location just shows its raw coordinates rather than a resolved address (the manual-address fallback is identical either way). After OTP verification, both pages check whether that capability already exists on the account (`GET /workers|businesses/me/profile`) and show its read-only status instead of the form if so — mirrors `partner-app`'s `ChooseCapabilityScreen` logic, just inlined per-page instead of a separate chooser screen, since a public visitor already arrived via a capability-specific link.

**`admin-web`'s `AdminLoginPage` is login-only** (no registration fallback, unlike `PhoneAuthFlow`) — `admin` accounts are provisioned via `backend/scripts/seedAdmin.ts`, never self-registered. Reuses the same `/auth/login/*` endpoints; rejects client-side if the returned account isn't `role: 'admin'` (the real enforcement is server-side `authorize('admin')` on every `/admin/*` backend route — this is only a friendlier message, per `docs/api-guidelines.md`'s "server-side, not just UI-hidden" rule). `RequireAdmin` gates every other route in this site the same way, redirecting to `/login` rather than rendering a broken dashboard for a logged-out or non-admin visitor.

**`AdminDashboardPage`** shows tabs (Workers/Businesses) × a verification-status filter (default `pending_verification`), each row linking to **`AdminProfileDetailPage`** — one component parameterized by a `capability` prop (mirrors `partner-app`'s `MyInfoScreen` dual-purpose pattern), with `AdminWorkerDetailPage`/`AdminBusinessDetailPage` as thin route-level wrappers supplying that prop. Approve/Reject calls `PATCH /admin/{workers|businesses}/:id/verification`. This page keeps its own inline header (not `PageHeader`) since it needs a right-side logout action `PageHeader` doesn't support — same "wrapper component for header-triggered local state" pattern the mobile apps' `HomeHeader`/`ProfileHeader` already established.

## Account Model

Every self-registered account is a plain `user` — not one of an exclusive set of roles chosen at registration. **Worker and Business are optional capabilities** a `user` account can add, either during onboarding (Home menu → "Are You a Worker?"/"Do You Have a Shop?") or, in principle, at any later point — not an exclusive choice made once at signup. Adding a capability creates a linked `worker_profiles`/`business_profiles` row (backend modules `workers`/`businesses`, each owning its own table per the module-boundary rule above) whose own `id` is that capability's distinct identifier (worker_id / business_id) and whose own `verification_status` (`pending_verification` → `verified`/`rejected`) gates admin trust for that capability specifically — independent of `accounts.status`, which is `active` immediately for every self-registered account regardless of which capabilities it later gains. `business_staff` (an employee added by a business owner) and `admin` are unrelated to this model — provisioned differently, never self-registered. This superseded an earlier design where `role` was chosen once at registration (`user`/`worker`/`business_owner`) and Worker/Business accounts sat in `pending_verification` from the moment the account itself was created; `WelcomeScreen`'s three role-selection cards were removed accordingly (see above).

**Image uploads (Cloudinary)**: both `workers` and `businesses` modules' `POST .../me/profile` endpoints accept `multipart/form-data`, parsed by a shared `multer` instance (`backend/src/common/middleware/upload.ts` — disk storage to a temp dir, images only, 8MB/file limit) ahead of `validateBody` in the route chain (multer populates `req.body`/`req.files` first, which `zod` then validates — text fields all arrive as strings, so the `workers`/`businesses` validation schemas use `z.coerce` for anything numeric, unlike the JSON-body schemas elsewhere in the app). `backend/src/common/services/cloudinaryService.ts`'s `uploadToCloudinary(filePath, folder)` uploads to Cloudinary and always deletes the local temp file afterward, success or failure — mirrors a pattern already proven in a sibling project, but configured via this app's own `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` env vars (never hardcoded, never shared across projects); if they're unset, `uploadToCloudinary` throws a clear `CLOUDINARY_NOT_CONFIGURED` `AppError` rather than the server failing to boot at all.

**Removed/replaced photos and deleted profiles clean up Cloudinary storage, not just the DB row** — `deletePhotosFromCloudinary(urls)` (same file) is best-effort: a Cloudinary failure is logged and skipped, never thrown, since a storage-cleanup hiccup must never block the user's actual profile update/delete from succeeding. Only the photo URL is persisted (no separate public_id column), so `extractPublicIdFromUrl(url)` parses Cloudinary's own URL structure (`.../upload/v{version}/{public_id}.{ext}`) to find what to delete — both modules' `updateProfile` diff the incoming `existingPhotoUrls` against what's currently stored and delete whatever's no longer kept; `deleteProfile` deletes every photo before removing the row. Any future module storing Cloudinary photo URLs should follow this same "URL is the only source of truth, derive the public_id when cleanup is needed" pattern rather than adding a parallel public_id column.

**Multer's own errors (file too large, wrong type) are mapped to specific responses, not the generic 500** — `multer.MulterError` (thrown internally when a file exceeds `upload.ts`'s size/count limits) and the file-type filter's rejection are neither `instanceof AppError`, so without explicit handling both fell through `errorHandler`'s catch-all into a bare "Something went wrong" 500 with no indication of the actual problem. `errorHandler` (`common/middleware/errorHandler.ts`) now special-cases `err instanceof multer.MulterError` → 400 with a `FILE_UPLOAD_ERROR` code and a limit-specific message (oversized file vs. too many files); the file-type filter (`upload.ts`'s `fileFilter`) calls back with an `AppError.badRequest(..., 'INVALID_FILE_TYPE')` instead of a plain `Error`, so it's caught by the existing `AppError` branch instead of needing its own case. Any future multer-backed upload endpoint inherits this automatically through the shared `errorHandler` — no per-route handling needed.

**Every handled error is logged server-side, not just unexpected ones** — `errorHandler`'s `AppError` and `MulterError` branches both `logger.warn` (code/statusCode/path/details) before responding; previously only the generic-500 fallback logged anything, so a client-reported failure that the backend "handled correctly" (a 400/401/404/409) left zero server-side trace, making it pure guesswork to diagnose after the fact. `upload.ts`'s `logUploadedFiles` middleware (wired into all four Worker/Business multipart routes, right after `multer` parses the request and before validation) logs each received file's name/mimetype/size — so any future upload issue is diagnosable straight from the log instead of reasoned about blind from the client side.

## Auth Flow

1. Mobile number, email, and location entered → OTP sent.
2. OTP verified → account created (always `role: "user"`, `status: "active"` immediately) → logged in.
3. JWT access + refresh tokens issued.
4. Optionally, at any point: add Worker and/or Business capability (see Account Model above) — each starts `pending_verification` until admin approves, independent of the account itself.

## Authorization

Role-based: `user`, `worker`, `business_owner`, `business_staff`, `admin` (+ future admin sub-roles) — the enum is unchanged, but `worker`/`business_owner` are no longer assigned via self-registration (always `user`, see Account Model above); they remain in the type for any future non-self-registration assignment path. Every protected endpoint checks authentication (valid JWT) and authorization (role/permission) before executing business logic.

## Search Architecture

Area-based for MVP: users select village/town, workers/businesses define service areas — **however, full GPS coordinates are now captured at registration and for Worker/Business capability locations** (see Account Model above), a deliberate, confirmed override of the original "no live GPS in MVP" decision. Search itself is still area/village-town-based for now; the coordinates are captured and stored so radius-based search can build on them later without another migration. Search service is isolated behind an interface so that swap can happen without touching booking/order business logic.

## Verification (PIN) Architecture

```
Booking/Order created → backend generates unique single-use PIN → stored securely
    → customer shares PIN with worker/business staff → PIN submitted → backend verifies
    → status updates only on successful verification
```

Never SMS OTP for this step — in-app only, free, per-booking/per-order.

## Notification Architecture

Firebase Cloud Messaging via a dedicated `notifications` service — never triggered directly from controllers. Other modules call `notifications.service` to enqueue a send.

## Database

PostgreSQL, normalized. Core entities: accounts, otp_verifications, refresh_tokens, worker_profiles, business_profiles, business_staff, bookings, orders, order_items, notifications, reviews, ratings, verification_requests, audit_logs. Foreign keys enforce relationships; index mobile_number, email, skill_category, shop_category, service_area (and other frequently-filtered columns). Full DDL lives in `docs/database.md` / `database/migrations/`.

## Localization Architecture

Language is a core architectural concern, not a display-layer afterthought — see `docs/localization.md` for the full model. The load-bearing points for any module you build:

- `accounts.preferred_language` is the authoritative per-account language; local device storage is a convenience cache synced from it after login.
- APIs are language-independent — never branch business logic on language, never localize API `message`/error text server-side for the client to display. The mobile client maps `error.code` → localized string itself.
- Anything the backend composes and pushes to a user unprompted (notifications, admin announcements) *is* language-aware, but via per-language template lookups keyed by the recipient's `preferred_language` — not translation-on-the-fly.
- Reference/category data (worker professions, business categories) is stored as a stable language-independent code with per-language label lookups, never as translated strings that get re-translated for display.

## Future Microservices Migration

When a module needs independent scaling (e.g., Notifications or Search under load), extract it because:

- It already exposes a clean service-layer interface.
- It owns its own tables/repository (no cross-module direct queries).
- Its inter-module calls are already abstracted, so they become network calls (REST/queue) instead of in-process calls with minimal contract change.

No module should ever query another module's tables directly — this is the rule that keeps the split cheap later.
