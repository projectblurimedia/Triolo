# Project Context (Living Memory)

Update this file whenever product state changes: completed modules, pending work, schema, APIs, decisions. This is the "what" — see [[cloud.md]] for the "how".

## Product Vision

Local-services marketplace for India. MVP launches in Telugu-speaking states, then expands nationwide. Three account types — **User**, **Worker**, **Business** — plus an internal **Admin** system. Full detail: `docs/product-specification.md`.

## MVP Scope Snapshot

- Auth: mobile OTP + JWT. Every self-registered account is a plain `user` (captures at minimum full name + mobile at registration; email and location are optional at the API level — `user-app` still collects both, `partner-app` collects neither, see "Account Model" below) — Worker and Business are **optional capabilities** added afterward (during onboarding or later, from Home's menu), not an exclusive role chosen at signup.
- Worker discovery: broadcast (expanding radius) + manual filtered search.
- Worker booking: PIN-verified arrival, full status pipeline through to rated/closed.
- Business ordering: shopping-list model, per-item availability review, PIN-verified pickup/delivery.
- Admin: verification queues, user/worker/business management, complaints, warnings, suspension/blocking, announcements, audit logs.
- Location: **full GPS coordinates** now captured (registration, Worker service location, Business shop location) — see "Key Technical Decisions" below; this overrides an earlier "no live GPS in MVP" decision. Search itself is still area/village-town-based for now; the captured coordinates are there for radius-based search to build on later.
- Language: core architectural requirement, not a nice-to-have — English + Telugu from MVP, account-level `preferred_language` synced with device storage, first-launch language picker, registration-time language capture, settings-time backend sync. Full model in `docs/localization.md`. No feature ships without both languages.
- No SMS OTP for service completion anywhere — always backend-generated single-use in-app PINs.

## Account Model

Every self-registered account is a plain `user` — not one of an exclusive set of roles chosen at registration. **Worker and Business are optional capabilities**, added via `partner-app`/`registration-web` (not `user-app` — see that app's own Completed Modules entry for why the Home-menu entry points were removed): a `user` account can add a Worker profile (one or more skill categories, experience, structured service address, portfolio photos) and/or a Business profile (shop name, one or more shop categories, structured shop address, shop photos, delivery availability + per-km price). Each capability is its own row (`worker_profiles`/`business_profiles`, owned by the new `workers`/`businesses` backend modules) with its own generated id (worker_id / business_id) and its own `verification_status` (`pending_verification` → `verified`/`rejected`) — independent of `accounts.status`, which is `active` immediately for every self-registered account. `business_staff` (an employee added by a business owner) and `admin` are unrelated to this model — provisioned differently, never self-registered.

This superseded an earlier design (role chosen once at registration, Worker/Business accounts starting `pending_verification`) — `WelcomeScreen`'s three role-selection cards were removed, `RegisterScreen` no longer takes a `role` param at all.

**Account registration itself only strictly requires `fullName`/`mobileNumber`** — `email`/`latitude`/`longitude`/`locationAddress` are all optional at the `POST /auth/register/request-otp` API level (`accounts.email`/`.location_address` were already nullable at the DB level; only the API validation required them, and that requirement is what was relaxed). `user-app`'s `RegisterScreen` still asks for all of them (a consumer account benefits from having a location on file even if it never adds a capability); `partner-app`'s `RegisterScreen` asks only for Full Name + Mobile Number, per explicit product decision — a partner going on to add a Worker/Business capability supplies a far more detailed, structured address in that flow anyway (see the Workers/Businesses migration `0008` note below), so asking for a location twice was pure friction. `Account.email`/`AuthAccount.email` (backend and both mobile apps' local types) are typed `string | null` accordingly; every UI that displays it already guards against (or was fixed to guard against) it being absent.

  - **Bug fix (same follow-up, found immediately after shipping the above) — the marquee never actually animated; it silently fell back to a native "…" instead.** Root cause: the first version measured the *visible* copy of the text directly (an `Animated.Text` with `alignSelf: 'flex-start'`, no explicit width, inside the fixed-width `overflow: 'hidden'` wrapper) and assumed a normal-flow text node with no width style reports its true, unconstrained content width via `onLayout`. It doesn't — RN/Yoga passes the parent's available width down as an upper bound to a normal-flow text node's own measurement pass regardless of `alignSelf`, so the reported width was always clamped to `containerWidth`, `textWidth <= containerWidth` was therefore always true, no animation ever started, and the default `ellipsizeMode` ("tail") quietly drew a trailing "…" instead — which is exactly the "showing … instead" report. **Migration `0008` — structured Worker/Business address** (explicit product decision): `worker_profiles`/`business_profiles`' single free-text `location_address` column was replaced with `area` (nullable — street/locality/landmark), `city`, `district`, `state` (all required), and `pincode` (required, `CHECK (pincode ~ '^[0-9]{6}$')`, India 6-digit) — a manual one-line address wasn't precise enough to ever support area/pincode-based filtering later. `latitude`/`longitude` are unchanged. New indexes: `idx_worker_profiles_city`/`_pincode`, `idx_business_profiles_city`/`_pincode`. This is scoped to the Worker/Business **capability** location only — `accounts.location_address` (captured once at registration, for the account itself) is untouched and out of scope. The migration `TRUNCATE`s both tables first (existing pre-launch test profiles wiped per explicit instruction, since there's no reliable way to auto-split old free-text addresses into the new columns) — every account can simply re-register its Worker/Business profile with the new structured fields. Every layer updated in the same change: `workers`/`businesses` modules' `dto.ts`/`validation.ts`/`repository.ts`/`service.ts` (zod requires `city`/`district`/`state`/`pincode`, `area` optional), both modules' unit tests (72 backend tests still passing), and all four frontends — `user-app`/`partner-app` gained a new shared `AddressPicker` component (City/District/State/Pincode/Area as five always-editable fields; "Use my current location" still reverse-geocodes via `expo-location` and pre-fills what it can, but — unlike the old `LocationPicker`, which is untouched and still used by `RegisterScreen`'s account-level location — editing a field afterward no longer clears the detected lat/lng), `registration-web` gained an `AddressField` (same fields, no reverse-geocoding available there so GPS only captures lat/lng in the background), and `admin-web`'s profile detail page now shows the joined address via a small `formatAddress()` util (duplicated per-app, same "no shared package" convention as everything else cross-app) instead of the raw `locationAddress` string. `WorkerProfileCard`/`BusinessProfileCard`/`MyInfoScreen` all updated to the same `formatAddress()` display.

New `constants/indiaLocations.ts` (duplicated across `user-app`/`partner-app`/`registration-web`) holds `INDIA_STATES` (28 states + 8 UTs) and `INDIA_DISTRICTS_BY_STATE` — a point-in-time snapshot flagged in its own doc comment for periodic re-verification, since district boundaries change. District options cascade off the selected state and reset if they're no longer valid for a newly-picked state. Mobile apps got a new shared `SelectField`/`SelectModal` (a `TextField`-styled tap target opening a full-screen searchable list, matching `NearbySearchModal`'s chrome); `registration-web` just uses native `<select>`/`<option>` (new `.field select` CSS rule). GPS-based auto-fill on `AddressPicker` now only sets State/District when the reverse-geocoded name actually matches an entry in the fixed list, leaving it blank for manual selection otherwise rather than storing an unlisted value.
  - **Bug fix (same module, follow-up pass)**: District often wasn't auto-selecting after "Use my current location," reported from `partner-app`. Root cause: `matchInList`'s exact (case-insensitive) comparison was too strict for real reverse-geocoder output — Android/iOS geocoders frequently return a district-level name with a "District" suffix, different spacing, or in a different field (`subregion` vs `district` vs `city`) than this hand-typed list expects, so an exact match often failed silently with no feedback. Fixed by (1) normalizing both sides (strip a trailing "district" word, collapse whitespace) before comparing, (2) falling back to substring containment either direction when the normalized exact match fails, (3) trying `subregion`, then `district`, then `city` in turn as the candidate source instead of committing to one, and (4) showing a toast ("we detected your state but couldn't match your district — please select it") whenever auto-fill genuinely can't determine the district, so the gap is visible instead of silently confusing. Applied identically to both `user-app`'s and `partner-app`'s `AddressPicker` copies.
  - **Follow-up (partner-app only)**: `partner-app`'s `RegisterScreen` (account creation) now asks only for Full Name + Mobile Number — email and location were dropped from this screen per explicit product decision, since a partner going on to add a Worker/Business capability supplies a far more detailed structured address in that flow anyway, making a second, cruder location prompt pure friction. **pg gotcha fixed in the same change**: node-postgres only auto-parses array columns of *built-in* types — arrays of custom enum types (like `worker_skill_category[]`) come back as the raw Postgres array-literal string (`"{electrician,other}"`) rather than a JS array, since pg has no registered type parser for custom-enum-array OIDs. Fixed via a small `parsePgArray` util (`backend/src/common/utils/pgArray.ts`) applied in both repositories' row-mapping functions. Also fixed in this change: the shared `pg.Pool` (`backend/src/config/database.ts`) had no `.on('error', ...)` handler, so an idle-connection reset from Supabase (routine, happens periodically) crashed the entire Node process via Node's unhandled-`'error'`-event contract — this was the actual root cause of intermittent "something went wrong" failures reported during registration/profile submission, since the whole server would silently die and stay dead until manually restarted. Now logs and survives it.

## Key Technical Decisions

- Modular monolith, feature-based backend modules (routes/controller/service/repository/validation/dto/tests each).
- PostgreSQL as default DB.
- PIN verification (not SMS OTP) for all service-completion steps; PINs are backend-generated, single-use, per-booking/per-order.
- **Full GPS coordinates captured** (registration location, Worker service location, Business shop location) — a confirmed, deliberate override of an earlier "no live GPS in MVP, area-based only" decision. Search itself remains area/village-town-based for now; the coordinates are stored for radius-based search to build on later without another migration.
- Account model: every self-registered account is `role: "user"`; Worker/Business are additive capabilities with their own tables/verification status, not an exclusive role — see "Account Model" above.
- Image uploads: backend-mediated Cloudinary (multer → temp disk → Cloudinary → cleanup), never exposing the API secret to the client. Each user supplies their own Cloudinary credentials via env vars.
- Business staff share one dashboard with real-time sync; permission-scoped actions.
- Order/booking cancellation locks once business review / worker-PIN-verification begins; only business/admin can cancel past that point.
- Localization: language is a first-class account attribute (`accounts.preferred_language`), not a purely client-side setting; client never displays raw API error messages, only `error.code` mapped to a localized string.
- **Editing a Worker/Business profile keeps its existing `verificationStatus` — it no longer resets to `pending_verification`.** This reverses an earlier design (documented here for a while: "editing resets to pending, since a verified profile changing its details hasn't been reviewed in its new form") per explicit follow-up feedback that partner-app's edit flow shouldn't demote an already-verified profile just for adding a photo. `WorkersService.updateProfile`/`BusinessesService.updateProfile` now pass `verificationStatus: existing.verificationStatus` through to the repository instead of hardcoding `'pending_verification'` — shared logic, so this applies identically to `user-app`'s `WorkerProfileModal`/`BusinessProfileModal` edit mode and `partner-app`'s `WorkerRegistrationScreen`/`BusinessRegistrationScreen` edit mode. Admin still gets visibility into edits, but as plain information rather than a re-review gate: `worker_profiles`/`business_profiles.updated_at` (already existed, already returned by the admin-facing `WorkerProfileWithAccount`/`BusinessProfileWithAccount` types) is now also typed and displayed in `admin-web` — "Registered `<date>`" plus, when different, "Last updated `<date>`" on `AdminProfileDetailPage`, and a compact "Edited `<date>`" caption on `AdminDashboardPage`'s list rows when a profile has been edited since its original submission. Deleting a profile is still a hard delete (no soft-delete/archive), reachable from Home menu → the profile form's own "Delete" action, or the `pen` edit button on `WorkerProfileCard`/`BusinessProfileCard` (user-app) / `MyInfoScreen`'s header (partner-app) — all entry points open the same edit-mode form with the existing profile passed in.

- **Backend is deployed on Vercel as a serverless function** (`https://triolo-backend.vercel.app`), not Render — Render was tried first but asked for card details even for its free tier, so the user switched. `backend/api/index.js` is the serverless entry point: a plain JS file (deliberately not TS, so there's no path-alias resolution for Vercel's function bundler to get wrong) that `require()`s the already-`tsc`+`tsc-alias`-compiled `dist/app.js` (built via `backend/vercel.json`'s `buildCommand: npm run build`) and re-exports `createApp()`'s return value directly — an Express app is itself a valid `(req, res) => void` handler, so no adapter is needed. `vercel.json`'s `rewrites` sends every path to `/api/index` while leaving the original `req.url` intact, so the Express app's own internal routing (`/health`, `/api/v1/...`) works unchanged from how it behaves under `server.ts`'s plain `app.listen()` locally. Deployed via `vercel link --project triolo-backend` + `vercel env add ... --value ... --yes` (11 env vars — same values as `backend/.env` except **freshly generated `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`**, not the local dev placeholders) + `vercel deploy --prod --yes`, all non-interactively since this environment has no real TTY for CLI prompts (see the EAS keystore note elsewhere in this file for the same underlying constraint). `backend/vercel.json`/`api/index.js` and root `.gitignore`'s `.vercel/` entry are committed; the Vercel project link itself (`.vercel/project.json`) is not.
  - **Gotcha that broke the first deploy**: Supabase's *direct* connection hostname (`db.<project-ref>.supabase.co`, the one `backend/.env` uses for local dev) is IPv6-only on Supabase's free tier, and Vercel's serverless Node runtime has no outbound IPv6 support in the `iad1` region — every DB query failed with `getaddrinfo ENOTFOUND db.<ref>.supabase.co`, even though `/health` (no DB touch) returned 200 fine, which is what made it look like a generic "deployment is broken" issue rather than a DNS/connectivity one specifically. Fixed by switching the deployed `DATABASE_URL` (Vercel env var only — `backend/.env`'s local value is untouched and still uses the direct connection, which works fine from a long-lived local Node process) to Supabase's **connection pooler** (Supavisor) string instead: `postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres` — found under Supabase dashboard → Project Settings → Database → Connection pooling → Transaction mode. The pooler hostname is IPv4-reachable specifically to solve this exact serverless/edge connectivity problem; this is a standard, documented Vercel+Supabase pairing gotcha, not specific to this codebase. Any *other* service ever deployed to a serverless/edge platform (Vercel, Lambda, Cloudflare Workers, etc.) against this same Supabase project must use the pooler connection string too, not the direct one.
  - `user-app/src/constants/config.ts`'s `API_BASE_URL` now branches on `__DEV__`: the LAN IP in Expo Go/dev-client (unchanged), or `process.env.EXPO_PUBLIC_API_URL` (falling back to a hardcoded `FALLBACK_PROD_URL` matching the Vercel URL) in a built app — same env-driven pattern already proven in a sibling project (CampuSphere's `serverConfig.js`). `EXPO_PUBLIC_API_URL` itself is set per build profile in `user-app/eas.json` (`preview`/`production`), not hardcoded in app source, so pointing a future build at a different backend is a one-line `eas.json` edit.
- **Backend dev workflow gotcha (not a code bug, but has repeatedly looked like one)**: `backend/package.json`'s `dev` script (`tsx watch src/server.ts`) auto-reloads on source changes — that's the mode to run while developing. `npm start` (`node dist/server.js`) does **not** auto-reload; it serves whatever was last compiled by `npm run build`, which can silently drift out of sync with `src/` for days. This was caught directly: `src/modules/auth/validation.ts` had `email`/`locationAddress` made optional (see Account Model above), but a live request against the running server still rejected them as `Required` — the running process turned out to be serving a `dist/` build compiled *before* that change (confirmed by comparing `dist/modules/auth/validation.js`'s content and mtime against `src/modules/auth/validation.ts`). Rebuilt `dist/` to resolve it. If a backend behavior change doesn't seem to be taking effect despite the source clearly being correct, check which mode the running process is in before assuming the code is wrong — restart under `npm run dev`, or `npm run build` again, before debugging further.
